## 一、环境实践类

### Q1 <a id="q1"></a>我的机器已经是 qemu-kvm 虚拟机（嵌套虚拟化），IOMMU 需要单独开启吗？如何开启？

**要区分两层**：物理机的 IOMMU（VT-d）在 BIOS 里开；而虚拟机里的 IOMMU 是 QEMU **模拟出来的虚拟硬件（vIOMMU）**，不会自动存在，也**不能在 VM 内部开启**——必须在启动这台 VM 的 QEMU/libvirt 配置里显式添加。

```
物理机 (BIOS 开 VT-x/VT-d)          ← vIOMMU 不在这里管
  └─ 你的 VM（当前机器）             ← vIOMMU 要在这里的启动参数里加
      └─ 学习用 VM（课程 labs）
```

**先想清楚要不要开**：`check-vt.sh` 的 `[5]` 只是 ⚠️ 警告，不影响通过判定。
学习 KVM、跑嵌套 VM 完全不需要 IOMMU，真正要修的是 kvm 模块和 /dev/kvm 权限。
只有做 **lab07 PCI 直通（VFIO）** 才需要它。

**开启方法**（需控制外层启动配置，机型必须 q35）：

```bash
# 方式一: 裸 QEMU
qemu-system-x86_64 \
    -machine q35,accel=kvm \
    -cpu host \
    -device intel-iommu,intremap=on,caching-mode=on \
    ...
```

- `caching-mode=on`：用了 vhost（virtio-net 默认 `vhost=on`）时必须加
- 要直通的设备需挂在 `pcie-root-port` 后面才会被 vIOMMU 管辖

```xml
<!-- 方式二: libvirt domain XML, <devices> 内加一行 -->
<iommu model='intel'/>
```

**guest 内核**：命令行加 `intel_iommu=on`（部分发行版默认已开，显式加最保险）。

**验证**：

```bash
dmesg | grep -iE 'dmar|iommu'     # "DMAR: IOMMU enabled"
ls /sys/class/iommu/              # dmar0
ls /sys/kernel/iommu_groups/
```

即使开了 vIOMMU，嵌套场景下想做真实设备直通，还要求外层宿主机先把某个真实
PCI 设备 VFIO 直通进你这台 VM——链路上每一层都得有条件。纯学习环境没有多余
物理设备时，`[5]` 的警告可以放心忽略。

### Q2 <a id="q2"></a>Debian 13 (trixie) 执行 install-qemu.sh 报 "软件包 qemu-efi 没有可安装候选"

**原因**：Debian/Ubuntu 根本没有 `qemu-efi` 这个包。UEFI 固件包名是：

| 固件用途 | Debian/Ubuntu 包名 |
| --- | --- |
| x86 UEFI | `ovmf` |
| ARM (AArch64) UEFI | `qemu-efi-aarch64` |

x86 机器只需 `ovmf`，连 `qemu-system-arm` 都不用装。脚本已修复为：

```
qemu-system-x86 qemu-utils qemu-kvm bridge-utils
libvirt-daemon-system libvirt-clients libvirt-daemon
virt-manager virt-viewer ovmf genisoimage
cloud-image-utils libguestfs-tools
```

**注意**："选中 'qemu-system-x86' 而非 'qemu-kvm'" 的提示是正常的——Debian 里
`qemu-kvm` 只是别名/过渡包，KVM 加速能力不受影响。

### Q3 <a id="q3"></a>`-kernel /dev/null` 报 `could not load kernel '/dev/null': No such file or directory`

**原因**：`-kernel` 需要一个**真实的内核镜像文件**（QEMU 会探测 ELF/bzImage 格式）。
`/dev/null` 是零字节字符设备，加载必然失败；那句 "No such file or directory"
是 QEMU 报了个误导性的 errno，不是文件真不存在。

**正确验证 KVM 的姿势**（`-S` 让 CPU 暂不执行 + monitor 查询）：

```bash
qemu-system-x86_64 -machine accel=kvm -m 512 -nographic -S -monitor stdio
```

```
(qemu) info kvm
kvm support: enabled     ← 看到这个就是 KVM 加速在工作
(qemu) quit
```

两个相关坑：

- 报 `failed to initialize kvm: Permission denied` → kvm 模块没加载或
  `/dev/kvm` 权限没生效（`usermod -aG kvm` 之后要**重新登录**）
- `accel=kvm` 失败会直接报错退出，**不会**悄悄回退 TCG；写 `accel=kvm:tcg` 才会回退

### Q4 <a id="q4"></a>`qemu-system-x86_64 ... -S -pidfile /tmp/x.pid` 执行完就卡住了

**不是卡住**——这条命令是前台运行的，QEMU 正在正常跑。因为加了 `-S`（CPU 暂不执行）
又没有磁盘/内核，没有任何输出，看起来像挂了。文档里那行末尾的 `&` 是故意放后台的。

**退出方式**：

1. `Ctrl-A` 松开后再按 `x` —— `-nographic` 模式下 QEMU 的退出快捷键
2. 另开终端：`kill $(cat /tmp/x.pid)`

`-nographic` 时 stdio 被 QEMU 复用成控制台，常用快捷键：

| 快捷键 | 作用 |
| --- | --- |
| `Ctrl-A x` | 退出 QEMU |
| `Ctrl-A c` | 在虚拟串口 / QEMU monitor 之间切换 |

日常学习更推荐交互式：`-monitor stdio` 直接看到 `(qemu)` 提示符。

## 二、硬件原理类

### Q5 <a id="q5"></a>EPT 方案下，每个 guest 都有各自的 CR3 吗？

**要更精确：CR3 不是 guest 的"私产"，而是每个 vCPU 上的物理寄存器**，
任意时刻一个 vCPU 上只有一个 CR3 值。

| 层面 | 谁的 CR3 | 内容 |
| --- | --- | --- |
| guest 内部 | 每个进程各有一个页表 | guest OS 切换进程时自己写 CR3（装的是 **GPA**） |
| 多个 guest | 每个 vCPU 有自己的 VMCS | VMCS 里存 `GUEST_CR3` 和 `EPTP`，VM entry 时加载 |
| 同一 guest 的多个 vCPU | 通常共享同一份 EPT | EPT 是 guest 级的 stage-2 表，不是每进程一份 |

两种方案下 CR3 里装的东西完全不同：

```
影子页表:
  硬件 CR3 = 影子页表的 HPA        ← VMM 偷换过的
  GUEST_CR3(VMCS) = guest 想装的值 ← 被监视、被同步

EPT:
  硬件 CR3 = guest 写的原样值(GPA) ← 不用偷换
  EPTP(VMCS) = stage-2 表的 HPA    ← 硬件自动做第二段转换
```

地址转换：

```
GVA ──CR3→ guest 页表 ──→ GPA ──EPTP→ EPT ──→ HPA
     └── 第一阶段: guest 自己管 ──┘└─ 第二阶段: 硬件/VMM ─┘
```

**关键洞察**：两层各自独立、各管一段。CR3 负责"进程 → GPA"，EPT 负责
"GPA → HPA"。guest 写 CR3 时硬件自动接上 EPT，所以 `mov cr3` 不再需要 VMM
截获同步——影子页表要 VMM 手动保持两张表一致（无穷 bug 之源），EPT 把同步
交给了硬件每次页表遍历，这就是"实现简单 10 倍"的根源。

TLB 里多个 guest 不串味靠 **VPID**（区分 vCPU）+ **EPTP tagging**（区分
stage-2）+ **PCID**（区分进程），VM 切换不用全量刷 TLB——这也是 `check-vt.sh`
检查 `vpid` flag 的原因。

### Q6 <a id="q6"></a>TLB miss 时，硬件如何知道当前跑的是 guest 还是 host？

**不是"猜"出来的——CPU 本身就处于明确状态里。** VMX 引入了处理器模式位：

- **VMX root 模式**：host/VMM（包括 host 上的普通用户进程）
- **VMX non-root 模式**：guest

这个模式位和 CPL 一样是 CPU 固有状态：`VMLAUNCH/VMRESUME`（VM entry）置位，
VM exit 硬件自动清掉。**任何时刻 CPU 都精确知道自己处于哪个模式**，页表遍历器
直接按模式选路线：

```
root 模式:   GVA ── host CR3 ──→ HPA                  （一阶段）
non-root:    GVA ── guest CR3 ──→ GPA ── EPT ──→ HPA  （两阶段）
```

TLB 项本身也带上下文标签（**VPID / PCID / EPTP**），查找时标签不匹配就当 miss。
guest 的翻译永远不会误命中 host 的 TLB 项。

**常见误区**：硬件区分的不是"guest 程序 vs host 程序"，而是 **root vs
non-root**。host 上的普通进程和 KVM 内核态都在 root 模式，待遇完全一样；只有
"进 VM 里了"才走两阶段翻译。

### Q7 <a id="q7"></a>guest 运行中被 host 中断打断，会走 VM exit 流程吗？

拆成两个不同的事件：

**事件一：物理中断（如 host 时钟 tick）到达而 vCPU 正在 guest 模式跑 → 会 VM exit**

KVM 打开了 VMCS 的 `external-interrupt exiting`——这是必须的，否则非 root 模式下
中断会直接经 **guest 的 IDT** 投递，host 自己的中断就打到 guest 头上了：

```
guest 运行 (non-root)
  └─ host 时钟中断到达 → VM exit (exit reason: external interrupt)
        └─ root 模式: KVM 转交 host 的 do_IRQ 处理
              ├─ 继续跑 vCPU → (必要时注入虚拟中断) → VMRESUME
              └─ 换进程跑 → 见事件二
```

**事件二：中断处理后 host 调度器换别的进程上 CPU → 没有第二次 VM exit**

CPU 在事件一就已退出到 root 模式。vCPU 本质是阻塞在 `ioctl(KVM_RUN)` 里的
普通 host 线程，调度器 preempt 它就是一次普通 Linux 上下文切换。下次调度回来，
从 KVM_RUN 返回点继续执行 VMRESUME，guest 无感恢复。

**补充**：

- host 时钟 tick 每次都造成 VM exit，tick 频率直接关系虚拟化开销
  （host 侧用 tickless/adaptive tick 优化）
- **注入给 guest 的虚拟中断**（guest 时钟、模拟设备）靠 APICv/posted interrupt
  硬件直投，尽量不触发 exit
- 直通设备（VFIO）的中断可走 posted interrupt 绕过 exit 直达 guest vCPU，
  这是 lab07 直通高性能的关键之一

### Q8 <a id="q8"></a>系统几千个进程，12 位（4096 个）的 PCID 能存下吗？

**存得下——PCID 根本不是"每进程一个的永久 ID"，而是每 CPU 上的临时缓存标签。**

三个事实：

**1. PCID 只有 4096 个，但系统从不需要那么多**
TLB 是**每核私有**的，一个核的 TLB 总共也就几千个表项。同一时刻一个 CPU 上
"活跃"的地址空间极少，几千个进程绝大多数根本没有 TLB 项存在。

**2. 进程的真正身份标识是另一回事**
Linux 里每个 `mm_struct` 有全局唯一、永不复用的 `ctx_id`（64 位计数器）。
PCID 只是"这个 CPU 当前把这个 mm 编号为几"的映射，同一进程在 CPU0 和 CPU1
上拿到的 PCID 可以不同。

**3. 内核实际只用一个很小的池子，用完就回收**
x86-64 Linux 每个 CPU 只保留 **6 个动态 PCID 槽位**（0 号保留给内核），轮转分配：

```
CPU 上切换进程:
  mm_A 装入 → 分配 PCID 5
  切到 mm_B → 分配 PCID 6     （A 的 TLB 项还在，保留）
  ...
  第 7 个新 mm 到来 → 池子转满
     → 回收最旧槽位，INVPCID 按标签刷掉旧项，再分配
```

最坏情况只是"回收时按标签刷一次 TLB"。选 6 这个小数字的历史原因：早期 CPU
（Sandy/Ivy Bridge）有 PCID 但没有 `INVPCID` 指令，池子小回收成本才可控。
`lscpu` 里同时有 `pcid` 和 `invpcid` 两个 flag 属于理想情况。

**虚拟化对照**：KVM 的 VPID（16 位，65536 个标签）同样从池子轮转分配、耗尽时
`INVVPID` 刷旧标签再复用。**"全局唯一身份"和"缓存标签"是分开的两层设计**——
前者必须永不重复，后者只要在缓存容量级别的窗口内不撞就行。

### Q9 <a id="q9"></a>如何进行 INVPCID？难道要遍历 mm_struct 的 ctx_id 置空？

**不需要遍历——"mm → PCID"的反查表在内核里根本不存在。**

**INVPCID 指令**：一条指令，操作数是 16 字节的 `{PCID, 线性地址}`：

| type | 助记 | 作用 |
| --- | --- | --- |
| 0 | individual-address | 作废指定 PCID + 指定线性地址的表项 |
| 1 | single-context | **作废指定 PCID 的全部表项** |
| 2 | all-context | 作废所有表项（含全局项） |
| 3 | all-context | 作废所有表项（保留全局项） |

软件只给出"标签号"，硬件在 TLB 里**按标签并行匹配并作废**——遍历是硬件电路做的。

**映射关系存在哪**：内核从不维护全系统的 mm→PCID 表，而是**每个 CPU 一张
6 槽位小表**：

```
cpu_tlbstate.ctxs[6]:            ← 每 CPU 一份: 槽位 → ctx_id
mm->context.ctx_id = 4821        ← mm 里只存身份，不存 PCID
```

换进程逻辑（简化自 `choose_new_asid()`）：

```c
/* 先看这个 mm 在本 CPU 是否已有槽位 */
for (asid = 0; asid < 6; asid++)
    if (ctxs[asid].ctx_id == next->ctx_id)
        return asid;              /* 直接复用，TLB 项都还在 */

/* 没有则轮转抢占下一个槽位 */
asid = next_asid++ % 6;
invpcid_flush_single_context(asid);   /* INVPCID type 1，一条指令 */
ctxs[asid].ctx_id = next->ctx_id;     /* "置空"就发生在这里 */
```

查询方向永远是**"本 CPU 的 6 个槽位 → 哪个 mm"**，不是"某个 mm → 哪些 CPU"。
你说的"置空"确实存在，但对象是 6 元素的每 CPU 数组，不是全系统 mm 链表。

**mm 销毁时其他 CPU 惰性处理**：`exit_mmap`/全量 flush 时，其他 CPU 只置
`invalidate_other` 标志；各 CPU 下次切换地址空间时顺手把非当前槽位逐个
INVPCID（最多 5 条指令），宁可多刷两个不相干的槽位也不做反查——
典型的"惰性 + 小常数上界"设计。

**为什么 mm 里不存 PCID**：PCID 是"每 CPU 视角"的临时编号（同一 mm 在 CPU0
是 3 号、CPU1 可能是 5 号），往 mm 里存等于存错误的数据结构；存全局唯一的
`ctx_id` 才安全——槽位表比对 ctx_id 就能发现过期关联。

**老 CPU 没有 INVPCID 的回退**：写 CR3 大锤全刷非全局表项，这也是池子只留
6 个的原因之一。

**同构设计**：KVM 的 VPID 处理一样——每 CPU 维护 vCPU→VPID 池子，复用前
`INVVPID single-context`，同样不遍历任何 VM 列表。

### Q10 <a id="q10"></a>TLB 有上千个表项，PCID 为什么只用 6 个槽位？

这里有一个**单位混淆**：上千是 TLB 的**表项数**（按页算），6 是 **PCID 槽位数**
（按地址空间算）。一个槽位保护的不是一个表项，而是**整个地址空间的所有表项**。

> 衣柜有几千个格子（表项），标签牌只有 6 个（地址空间）——格子多不等于需要几千个标签。

**决定槽位数的不是 TLB 容量，而是调度器的真实工作集**。PCID 要解决的核心场景是
同一 CPU 上两三个执行流高频来回切换（生产者/消费者 futex ping-pong、fork 后 COW
往返、syscall 密集往返）。一个 CPU 上"几分钟内 TLB 还有价值"的地址空间就那么几个：
当前正在跑的 1 个 + 很快切回来的 ping-pong 伙伴 1~2 个。

**6 槽 LRU 的收益递减论证**：

```
某 mm 被挤出 6 槽 LRU
  ⇒ 说明 CPU 在它上次运行后已跑过 ≥6 个别的地址空间
  ⇒ 它的表项即使带标签，也早被 TLB 容量自然淘汰得差不多了
  ⇒ 第 7 个及以后的槽位保不住任何有价值的东西
```

**成本端也在惩罚大池子**：

- `invalidate_other` 惰性刷新要遍历槽位：6 槽 = 最多 5 条 INVPCID，100 槽 = 99 条
- 老 CPU（Sandy/Ivy Bridge 有 PCID 无 INVPCID）回收只能写 CR3 大锤，池子越大挥得越勤
- 簿记状态随槽位数线性涨

> **TLB 容量决定"一个槽位能保住多少表项"，调度器工作集决定"需要几个槽位"。**
> 前者是上千，后者是个位数，两者本来就不是一个量纲。

ARM 是另一套思路：ASID 位宽更小但用"generation 代数 + 溢出滚代"回收，殊途同归。
想亲手验证：futex ping-pong 微基准 + `perf stat -e context-switches,dTLB-load-misses`，
对比内核参数 `pcid=off` 前后的差异。

### Q11 <a id="q11"></a>槽位只有 6 个，为什么会对应到 CR3 低 12 位的 4096 个值？

因为**"槽位"是软件概念，"PCID 字段"是硬件概念**，两者只在数值上恰好重合。

```
硬件层（SDM 规定）:
  CR3[11:0] = 12 位标签字段
  唯一规则: 写 CR3 时该值被"盖"到之后产生的表项上;
  查找按 (虚拟页号, PCID值) 匹配,值不等就 miss。
  硬件不解释语义,写 37 它就标 37。
```

4096 只是**标签命名空间的大小**——"可以有 4096 种取值"不等于"必须用满"
（酒店房号编到 4096，不代表你必须同时住满）。

```
软件层（Linux 策略）:
  从 4096 个取值里只挑 6 个做轮转池
  恰好用数字 1~6,"槽位号 = PCID 值"纯属实现上的顺手
```

内核用槽位号直接当 PCID 值只是省事（`ctxs[asid]` 的下标和标签值是同一个数，不用
换算）。写成 `pcid = 37 * slot + 5` 语义完全不变——硬件只要求"同一时刻同一标签
不指两个地址空间"，哪些值在用、怎么换，硬件一概不知。

**那硬件为什么给 12 位而不是 3 位？** 因为规格设计者和 OS 设计者对"怎么用"的
判断不同：

- 规格层：给一个足够宽的通用机制，**分配策略完全留给软件**。事实证明了这种分层：
  Linux 用 6 值固定池、FreeBSD 另一套分配器、ARM 用"代数+滚代"、KVM 的 VPID
  （16 位）又是另一种池子——同一机制四种策略，硬件全都不用改
- 策略层：Linux 论证过"超过 6 个并发地址空间的 TLB 保留毫无价值"，哪怕有 4096
  个值可用也只养 6 个

> **4096 是硬件给的上限，6 是软件算出的最优解。** 位宽回答"最多能隔离多少份翻译
> 缓存"，槽位数回答"值得养多少份"。

### Q12 <a id="q12"></a>「槽位 → mm 身份」那张表是硬件存的还是软件存的？

**纯软件**。`cpu_tlbstate.ctxs[6]` 是普通的每 CPU 内核变量（`DEFINE_PER_CPU`），
存在内存里，硬件完全不知道它存在：

```
硬件知道/存储的:                 软件知道/存储的:
  TLB 表项内容(含 PCID 标签)       ctxs[6] 槽位表(槽位 → ctx_id)
  CR3 当前值(含当前 PCID)          mm->ctx_id(全局身份)
  INVPCID 按标签作废这条规则       回收策略、轮转指针、invalidate_other 标志
```

硬件的全部承诺只有一条：**"标签 ≠ 当前 CR3 里的 PCID → 不命中"**。至于"哪个标签
属于哪个进程、什么时候该作废"，硬件不解释也不维护——全靠软件这张账本决定什么时候
发 INVPCID。这就是"机制归硬件，策略归软件"。

### Q13 <a id="q13"></a>同一进程在不同 CPU 上的 PCID 一样吗？过期时刷哪些表项？

**PCID 是每 CPU 视角的**，同一进程：

```
在 CPU0 上跑 → 占 CPU0 的 3 号槽 → CPU0 上该进程的新表项都带标签 3
在 CPU1 上跑 → 占 CPU1 的 5 号槽 → CPU1 上该进程的新表项都带标签 5
```

由此推出过期行为的精确边界：

- **本 CPU 内**：同一进程的所有翻译共享同一标签；对那个标签发 INVPCID type 1，
  该标签的全部表项**整批**作废（硬件按标签并行匹配，不是软件遍历）
- **只限本 CPU**：CPU1 里的副本（标签 5）纹丝不动，由 CPU1 走自己的失效流程
  （立刻刷，或置 `invalidate_other` 惰性刷）

两种"过期"触发（对应 Q9）：

```
① 抢槽回收: 第 7 个 mm 到来 → LRU 槽位被占 → INVPCID type 1
② 映射失效: mm 被 munmap/exit/全局 flush → 本 CPU 立刻刷,
            其他 CPU 惰性刷各自的非当前槽位
```

**复用安全性**：标签值可回收复用，但复用前必然刷过——看到相同标签不会撞上
"前任的旧表项"。

> 硬件只维护"标签 ↔ 表项"的对应；**"标签 ↔ 进程"的账本是软件的、每 CPU 一份**。
> 同一进程在同一 CPU 的所有表项共用自己的标签，过期时整批作废；跨 CPU 则各管
> 各的账本、各刷各的 TLB。

### Q14 <a id="q14"></a>TLB 里只放当前程序的表项吗？两个程序 ping-pong 怎么办？

**不是。TLB 在任一时刻是多标签混存的**——这正是 PCID 的意义所在。CPU0 TLB
某一时刻的快照：

```
表项: VA 0x7f00 页 → PA ...   标签 3   ← 程序 A(当前在跑)
表项: VA 0x6000 页 → PA ...   标签 5   ← 程序 B(刚被切走,余温还在)
表项: VA 0x7fc0 页 → PA ...   标签 3   ← 程序 A 的另一页
表项: VA 0xffff8... → PA ...  标签 0   ← 内核态翻译
```

**槽位限制的是"同时保留几个地址空间的翻译"，不是表项数**——一个程序占多少表项由
它的工作集决定（可能 1 个，可能几百个），上千表项在几个标签之间怎么分布完全随
访问模式走。

**ping-pong 正是 PCID 的初心场景**：

```
A 跑(标签3,积累表项) → 切到 B → B 跑(标签5,积累表项) → 切回 A → ...

切换动作本身: 写 CR3 换标签,不刷任何表项
切回 A 后:    A 的标签 3 表项原封不动,第一次访问照样命中
```

没有 PCID 时每次切换都要全量刷 TLB，B 跑的时候把 A 的翻译全冲掉，切回来全部
重新 miss，ping-pong 负载性能极差。

**混存天然安全的原因**：查找键是 **（虚拟页号，当前 CR3 的 PCID）** 二元组：

- A 在跑（标签 3）时，B 标签 5 的表项**对 A 不可见**——即使两者访问同一虚拟地址
- 所以同一 VA 可以同时存在两份不同标签的翻译（典型：fork 后 COW，父子进程同一
  地址映射不同物理页），互不串扰

> **槽位决定"TLB 里同时养着几个地址空间的翻译"，表项数由各程序自己的工作集决定。**
> 切换只换 CR3 里的标签不刷表；查找按（VA, 当前标签）精确匹配，混存既省事又安全。

## 三、QEMU 使用类（前后端模型）

### Q15 <a id="q15"></a>`-netdev`/`-drive` 是让宿主机做操作的？`-device` 是控制在 guest 里生成什么设备？

**方向正确，精确化为 QEMU 的前端/后端分离模型**，用 `id=` 牵线配对：

```
guest 侧（前端, -device）                host 侧（后端, -netdev/-blockdev/...）
┌─────────────────────┐                ┌──────────────────────────┐
│ virtio-net-pci      │ ←─ netdev=n0 ─→│ tap 内核接口 / SLIRP 协议栈│
│ virtio-blk-pci      │ ←─ drive=d0 ──→│ qcow2 驱动 → 打开的文件 fd │
│ (PCI 总线上的设备)    │                │ (QEMU 进程里的资源)        │
└─────────────────────┘                └──────────────────────────┘
```

| 选项 | 属性 | 干什么 |
| --- | --- | --- |
| `-netdev` | **纯后端** | 宿主机侧网络通路：tap / user / socket / vhost |
| `-blockdev` | **纯后端** | 宿主机侧：打开、解析镜像文件 |
| `-device` | **前端** | guest PCI 总线上出现什么设备，guest 装什么驱动 |
| `-drive` | **混合（legacy）** | 后端 + 前端一步到位（`if=` 部分是前端） |
| `-object` | **纯后端** | 其他宿主机资源：rng、memory-backend、tls-creds… |

**`-netdev` 细分**（都是宿主机侧，但机制不同）：

- `-netdev tap`：QEMU `ioctl(/dev/net/tun, TUNSETIFF)` 让内核创建 tap 接口；
  **"接网桥"不是 QEMU 做的**，是宿主机网络配置（qemu-ifup 脚本或 libvirt）
- `-netdev user`：**根本不创建 tap**——QEMU 进程内软件协议栈（SLIRP）做 NAT，无需 root
- `-netdev tap,vhost=on`：数据面下沉到内核 vhost 工作线程，QEMU 只管控制面

qcow2 解析同理：QEMU 的 block 层在**自己进程内**解析元数据、按 cluster 映射读写
宿主文件。

**`-device` 决定 guest 的"硬件现实"**：PCI 枚举看到什么 vendor/device ID、内核装
什么驱动（`virtio-net-pci` → `virtio_net`，`e1000` → `e1000`）、挂在哪条总线哪个
slot。同一后端可以换前端形态（`e1000` ↔ `virtio-net-pci`），同一前端也能换后端
（tap ↔ user）——分离的价值就在这。

**数据通路串联**（收一个网络包）：

```
物理网卡 → tap → QEMU netdev 后端 → 前端 virtio-net-pci 放入 virtqueue
  → 注入虚拟中断 → guest virtio_net 驱动 → 协议栈
```

**`-drive if=virtio` 是两件事压缩成一行**：

```bash
-drive file=x.qcow2,format=qcow2,if=virtio
#      └───── 后端: 打开/解析 qcow2 ─────┘└ 前端: 隐式创建 virtio-blk-pci

# 现代分离写法:
-blockdev driver=qcow2,node-name=d0,file.driver=file,file.filename=x.qcow2 \
-device virtio-blk-pci,drive=d0
```

> **记忆法**：`*dev`/`-object` 都是宿主机的资源清单，`-device` 都是给 guest 的
> 硬件清单，`id=` 是月老。

### Q16 <a id="q16"></a>`-drive` 会被淘汰掉吗？

**官方定位是 legacy，但短期内不会删除。**

- QEMU 文档已把 `-drive` 标为 legacy 接口，推荐 `-blockdev` + `-device` 分离写法
- **新特性只往 `-blockdev` 上加**：精细 cache 模式（`cache.direct`/`cache.no-flush`）、
  IO 线程绑定、块设备图（file → qcow2 → 过滤节点）、只读/共享写者语义等，`-drive`
  表达不了或很别扭
- 但存量太大——脚本、教程、老版 libvirt 全在用，删除兼容性代价极高。**libvirt
  的做法很说明问题**：用户写的还是传统 XML，它内部全部**转译成 `-blockdev`**
  再喂给 QEMU

> 结论：学习和小实验用 `-drive` 没问题；写管理工具、做精细调优（lab08 调
> cache/iothread 时）必须懂 `-blockdev`。

### Q17 <a id="q17"></a>display 和 monitor 感觉非常近似？

像是因为**它们用同一套"接到哪"的基础设施**（stdio / TCP / unix socket），甚至
`-nographic` 时被复用到同一条线上。但对话对象完全不同：

| | display（显示后端） | monitor（监控台） |
| --- | --- | --- |
| **对话对象** | guest 的显卡（帧缓冲） | **QEMU 进程本身** |
| **载荷** | 像素流 + 键鼠输入事件 | 管理命令：`info kvm`、`device_del`、`migrate`、`quit` |
| **guest 感知吗** | 感知（那就是它的显卡） | **完全不知道它的存在** |
| **协议** | VGA framebuffer / VNC / SPICE | HMP（人读）/ QMP（JSON，libvirt 用） |
| **类比** | 显示器 + HDMI 线 + 远程键鼠 | 蜷在 VMM 进程里的管理终端 |

> 一句话：**display 是 guest 对外的脸，monitor 是你对 QEMU 说话的嘴。**
> VNC 断了 guest 照常跑；monitor 里敲 `quit`，QEMU 进程直接退出。

**`-nographic` 的 mux 就是答案的一半**：它把 guest 串口控制台和 monitor 两个流
复用到同一条 stdio 上（`Ctrl-A c` 切换"对着谁说话"）。libvirt 实际用的是 QMP
（`-qmp unix:...`），JSON 格式的 monitor，机器可解析。

### Q18 <a id="q18"></a>`id=` 是月老，但为什么 `-blockdev` 例子没有 id？怎么配对？

**块设备层有两个命名空间**——`-blockdev` 创建的是块设备图上的**节点**
（BlockDriverState），命名用 **`node-name`**；块层的 `id=` 是**前端句柄**
（BlockBackend）的命名，配对时通常不用手写：

```bash
-blockdev driver=qcow2,node-name=d0,file.driver=file,file.filename=disk.qcow2
-device virtio-blk-pci,drive=d0
#                     ↑ 用 drive= 属性引用 node-name,隐式创建 BlockBackend
```

`-drive id=X` 之所以有 `id=`，是它一步创建了 BlockBackend（X 就是 id），节点名
自动生成（`#block123` 之类）。

**各后端的配对规则**：

| 后端类型 | 后端命名 | 前端配对属性 |
| --- | --- | --- |
| 网络 | `-netdev id=n0` | `-device ...,netdev=n0` |
| 块（现代） | `-blockdev node-name=d0` | `-device ...,drive=d0` |
| 块（legacy） | `-drive id=d0` | `if=` 隐式配对 |
| 字符设备 | `-chardev socket,id=c0` | `-device ...,chardev=c0` |
| 对象 | `-object rng-random,id=r0` | `-device virtio-rng-pci,rng=r0` |

块设备的图可以很长，链上每个节点各有 `node-name`，上游用 `file=` 引用下游：

```
virtio-blk-pci ──drive──> [qcow2 节点 node-name=d0] ──file──> [file 节点 node-name=f0]
```

> **确认**：是的，`-blockdev` 和 `-device` 必须通过 `node-name` ↔ `drive=` 精确
> 配对，名字错了启动直接报错。网络侧同理（`id=n0` ↔ `netdev=n0`）。

## 四、virt-install 与显示控制类

### Q19 <a id="q19"></a>`--os-variant alpinelinux3.18` 为什么需要指定 OS？KVM 和 guest 的 OS 没有关系啊？

**直觉对了一半**：hypervisor 层面（KVM 跑 CPU）确实与 OS 无关，但 libvirt/virt-install
构造的是整台虚拟"机器"——芯片组、设备模型、时钟——这些必须匹配 guest OS 的预期。
`--os-variant` 查 **libosinfo 数据库**，决定一堆默认值：

| 维度 | 例子 |
| --- | --- |
| 设备模型 | 新 Linux → virtio 磁盘/网卡；未知 OS → 保守 IDE/SATA + e1000（慢但兼容） |
| 机型 | 老 Windows 只认 i440fx；新版给 q35 |
| 半虚拟化优化 | Windows → 自动加 Hyper-V enlightenments；Linux → KVM pv features |
| 时钟 | Windows 用 localtime、Linux 用 UTC（否则 Windows 时间漂移） |
| 硬性要求 | Windows 11 → 强制 TPM + Secure Boot + q35 + OVMF |
| GUI 配套 | USB tablet（鼠标精准）、qxl 显卡配 SPICE |

不指定则退到"最保守通用配置"——能启动但性能差；新版可自动探测
（`--os-variant detect=on`）。

> **KVM 不关心 OS，但"这台虚拟机器长什么样"必须关心**。`--os-variant` 是管理层的
> 经验库，不是 hypervisor 的需求。

### Q20 <a id="q20"></a>`--noautoconsole` 不绑定当前终端，那绑定到了哪里？

**哪都不绑定——它只是"创建完就退出，不自动连上去"**。console 端点本身一直存在，
由 domain XML 定义：

- 图形控制台：VNC/SPICE 监听的 socket（`virsh dumpxml` 看 `<graphics>` 段）
- 串口控制台：pty / socket 上的 chardev

想连的时候随时接：

```bash
virt-viewer alpine-vm        # 图形控制台
virsh console alpine-vm      # 串口控制台（guest 里需配置 getty）
vncviewer :0                 # 裸 VNC 客户端也行
```

适合脚本化建 VM：`virt-install ... --noautoconsole` 挂后台，装系统交给 cloud-init
或稍后手动接。

### Q21 <a id="q21"></a>monitor 只提供命令行交互，不提供 GUI？

**协议层面：对**。HMP 是人读的文本命令，QMP 是 JSON 文本协议——都不渲染 guest 像素。

容易混淆的现象：用 `-display gtk`（或 SDL）时，GUI 窗口里**内嵌了 monitor 的"壳"**：
`Ctrl-Alt-1` guest 画面、`Ctrl-Alt-2` monitor 文本终端、`Ctrl-Alt-3` 串口。看起来
像 GUI，实际只是 GTK 窗口给文本协议套了个输入框，monitor 本身依然没有 GUI。
virt-manager 的图形化管理走 QMP/libvirt API——那是**别的程序在包壳**。

### Q22 <a id="q22"></a>guest 有多个显卡，display 会显示哪一个？

**display 后端（VNC/SPICE/gtk）只是个"探头"**，贴在某份帧缓冲上。多显卡 = 多份
帧缓冲：

- **boot 阶段**：firmware（SeaBIOS/OVMF）只初始化**主显卡（primary VGA）**，POST
  文字输出到它。主卡由 QEMU 决定——`-vga std` 指定的那块是主卡；`-device` 额外
  加的都是副卡，boot 期间黑屏
- **guest OS 起来后**：看 guest 驱动。Linux KMS 接管所有卡（每张一个
  `/dev/dri/cardN`），之后哪个头亮由 guest 编排；副卡在驱动加载前始终无输出
- **VNC 贴主卡帧缓冲**；SPICE + qxl 才支持多 head（多个 `-device qxl`，客户端
  显示多个屏幕）

实践建议：想指定主卡就显式写 `-vga`；混搭（`-vga std` + `-device virtio-gpu-pci`）
会遇到"boot 文字在 std 上、驱动加载后 KMS 把控制台抢走"的迁移闪烁——单卡或全
virtio-gpu（配 OVMF）更省心。

---

### Q23 <a id="q23"></a>QEMU monitor 和 guest 串口控制台是一回事吗？`Ctrl-Alt-2` 切的是哪个？

**不是一个东西**——而且 `Ctrl-Alt-2` 切出来的**不是** guest 的 tty，而是
**QEMU monitor**；guest 的串口 tty 在 `Ctrl-Alt-3`：

| 快捷键 | 端点 | 这条线上是谁在说话 |
| --- | --- | --- |
| `Ctrl-Alt-1` | guest 帧缓冲 | guest 显卡输出的画面 |
| `Ctrl-Alt-2` | **QEMU monitor** | **QEMU 进程（VMM）**，guest 完全不知道 |
| `Ctrl-Alt-3` | guest 串口（ttyS0） | guest 内核 / getty（需 guest 配置 getty 才有登录提示） |

**验证两者不同的方法**：

- 在 monitor 敲 `ls` → `unknown command`（它不是 shell）；敲 `info block` → QEMU
  秒答，guest 全程无感
- 在串口敲 `ls` → guest 里的 shell 执行；guest 没配 getty 时这里只有内核启动日志
  甚至空白

两者长得像（都是黑底白字文本终端），但一个通到 **VMM 进程**、一个通到 **guest
内核**——正是 Q17 "monitor 对话对象是 QEMU 而非 guest" 的实例。`-nographic` 的
`Ctrl-A c` 做的也是这两条线之间的切换。

**易混淆：`Ctrl-Alt-F2` ≠ `Ctrl-Alt-2`**——两套快捷键、两层归属：

| 组合 | 谁处理 | 效果 |
| --- | --- | --- |
| `Ctrl-Alt-F1..F7` | guest 内核（VT 子系统） | 在 **guest OS 内部**切 tty1~tty7 登录台，QEMU 只转发按键 |
| `Ctrl-Alt-1/2/3`（Ctrl-Alt 松开后再按数字） | QEMU 的 GTK/SDL 窗口 | 切换**窗口显示哪条流**（guest 画面 / monitor / 串口），不进 guest |

数字系列用两段式（按住 Ctrl-Alt 松开、再按数字）就是为了避开 guest 的
`Ctrl-Alt-*` 组合键。判断按键归谁的通用规则：`Ctrl-Alt-Fx` 先进 guest 键盘驱动；
QEMU 窗口菜单键（`Ctrl-Alt-数字`、`Ctrl-Alt-G` 抓取/释放鼠标、`Ctrl-Alt-F` 全屏）
由窗口拦截，guest 收不到。
