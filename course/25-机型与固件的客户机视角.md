# 25 · 机型与固件：客户机看到了什么

> 第 22 章讲了机型怎么被解析。这章再往下挖一层：`MachineClass.init()` 造出来的东西，
> 到底**通过什么通道**变成客户机能感知的"一块主板"？以及，UEFI 要正常枚举 PCIe，
> QEMU 必须先准备好哪些"内存里的东西"？

## 学习目标

- 说清客户机其实看不见"机型"这个词，它只看见一套硬件原语 + 固件表
- 列出 QEMU 让客户机感知机型的 6 条通道（总线 / 配置空间 / 地址映射 / ACPI / SMBIOS / fw_cfg）
- 说清 UEFI 枚举 PCIe 时，QEMU 负责什么、固件负责什么
- 明确回答：QEMU 需不需要"构造内存里的内容"？构造哪些？
- 从 ARM `virt` 视角对照 x86，理解"为什么没有 q35 那种二选一"

## 1. 思想实验：客户机根本不知道"机型"是什么

在客户机里跑 `lspci`、`dmidecode`、`dmesg`，你能看到一堆硬件信息，
但**没有任何一个寄存器写着 `machine=q35`**。机型是 QEMU 宿主机侧的概念。

客户机感知到的，是下面这些**具体事实**的并集：

```
  客户机看到的世界
  ├── 总线拓扑：有 pcie.0 吗？有多少根端口？
  ├── 设备清单：IDE 还是 AHCI？UHCI 还是 EHCI？
  ├── 每个设备的 PCI 配置空间（ID、BAR、能力列表）
  ├── 物理地址布局（谁在 0xFEC00000、ECAM 在哪）
  ├── ACPI 表（DSDT 描述主板、MCFG 描述 ECAM、MADT 描述中断）
  └── SMBIOS（dmidecode 里的"主板型号"）
```

**一句话**：机型不是"一个属性"，而是**一整组硬件原语 + QEMU 构造的表**。
不同机型 = 这组东西的不同组合。

## 2. `MachineClass.init()` 到底造了什么

回顾第 22 章，`pc_q35_init()` / `pc_piix_init()` / `virt` 的 `machvirt_init()`
是同一抽象的不同实现。它们都在做三件事：

1. **建总线树**：`pci.0` / `pcie.0` / `isa.0`，以及桥、根端口
2. **realize 设备**：给每个 `DeviceState` 建 `MemoryRegion`、挂总线、定地址
3. **生成固件可见数据**：ACPI 表、SMBIOS、device tree、fw_cfg

这三件事，正好对应下面 6 条"感知通道"。

## 3. QEMU 让客户机感知机型的 6 条通道

### 3.1 通道一：总线与桥的拓扑

i440fx 和 q35 造出的树结构不同，客户机一枚举就看得出来：

```
i440fx:  pci.0 (传统 PCI)  ← i440fx-pcihost    ── PIIX3 ISA
q35:     pcie.0 (PCIe 根复合体) ← q35-pcihost  ── ICH9 LPC
```

`lspci -t` 打印的树形结构，直接反映这个拓扑。

### 3.2 通道二：PCI 配置空间

每个设备（包括 host bridge 自己）都有一块**配置空间**（`PCIDevice.config` 缓冲区）。
客户机读到的关键字段：

| 字段 | i440fx | q35 |
| --- | --- | --- |
| host bridge Vendor:Device | `8086:1237` | `8086:29c0` |
| 配置访问方式 | 传统 `CF8/CFC` 端口 | ECAM (MMCONFIG) + `MCFG` |
| 南桥 | PIIX3 | ICH9 |
| SATA | IDE | AHCI |

> host bridge 的 ID 不同，是 OS/驱动分辨机型的**第一手证据**。

**配置空间的地址怎么访问**，两种机制：

- **i440fx（传统）**：I/O 端口 `0xCF8`（地址）/ `0xCFC`（数据）
- **q35（PCIe）**：**ECAM**（Enhanced Configuration Access Mechanism），
  一段 MMIO 窗口，每 4KB 对应一个 `bus:dev:func` 的 4KB 扩展配置空间
  （256 bus × 32 dev × 8 func × 4KB = 256MB，q35 默认基址 `0xB0000000`）

固件怎么知道 ECAM 在哪？—— 读 ACPI 的 **`MCFG`** 表（见 3.4）。

### 3.3 通道三：物理地址映射（MemoryRegion 树）

QEMU 把每个设备和固定控制器都映射到一个物理地址窗口：

```
0x00000000  RAM
0x80000000  PCI 32 位 MMIO 空洞（BAR 从这里分配）
0xB0000000  ECAM（q35）
0xFEC00000  IOAPIC       ← 固定
0xFEE00000  LAPIC        ← 固定
0xFED00000  HPET
0xFFC00000  固件 pflash（第 21 章）
0xFFFFFFF0  复位向量
```

用 `(qemu) info mtree -f` 能完整打印这棵映射树。客户机通过 ACPI `_CRS`
得知这些窗口的边界。

### 3.4 通道四：ACPI 表（**QEMU 主动构造的内存内容**）

这是"构造内存内容"最关键的一处。QEMU 在 `hw/i386/acpi-build.c` 里**现场生成**
一整套 ACPI 表：

| 表 | 内容 | 机型差异 |
| --- | --- | --- |
| `DSDT`/`SSDT` | 主板设备树、`_CRS`（资源窗口）、`_PRT`（中断路由） | q35 有 PCIe 根端口、hotplug 寄存器 |
| `MCFG` | ECAM 基址与大小 | **只有 q35 有** |
| `MADT` | CPU、IOAPIC、LAPIC 地址 | 通用 |
| `FADT` | 电源/复位等 | 通用 |
| `SRAT` | NUMA 拓扑 | 可配 |
| `HPET` | HPET 地址 | 通用 |
| `RSDP`/`RSDT`/`XSDT` | 根指针表 | 通用 |

**这些表不是写死在文件里的，是 QEMU 运行时按当前机型拼出来的字节流**，
然后通过 **fw_cfg**（见 3.6）投递给固件。

### 3.5 通道五：SMBIOS

QEMU 生成 SMBIOS 表（`hw/smbios/smbios.c`），客户机里 `dmidecode` 会显示：

```
System Information
    Manufacturer: QEMU
    Product Name: Standard PC (Q35 + ICH9, 2009)     ← 机型描述就在这里
```

机型的是否"可见"，在 SMBIOS 里最直白。

### 3.6 通道六：fw_cfg（QEMU → 固件的传话筒）

`fw_cfg`（`hw/nvram/fw_cfg.c`）是 QEMU 与固件之间的配置总线，通过 I/O 端口
`0x510/0x511`（或 DMA）访问，里面挂着：

```
etc/acpi/rsdp                 RSDP 指针
etc/acpi/tables               QEMU 构造的 ACPI 表块
etc/table-loader              表加载器（告诉固件怎么搬/重定位表）
etc/smbios/smbios-tables      SMBIOS
etc/e820                      内存布局
etc/boot-fail-wait            启动参数
opt/...                       其它运行时信息
```

SeaBIOS / OVMF 一开机就从 fw_cfg 里取这些，搬到客户机 RAM 并修好指针。

### 3.7（ARM 专属）通道七：Device Tree

x86 用 ACPI，ARM 传统上用 **Device Tree**。`virt` 机型在 `create_fdt()` 里
构造一棵 FDT，描述 CPU、GIC、内存、virtio-mmio、PCIe……直接放在内存里交给内核。
（`virt` 开了 `acpi=on` 时也会走 ACPI，和 x86 类似。）

## 4. 一条主线：从 init() 到 OS 看见的世界

```
MachineClass.init()
   │ 造总线树 + realize 设备 + 映射 MemoryRegion
   ▼
QEMU 构造 ACPI / SMBIOS / DT / fw_cfg    ← 真正写进内存的"内容"
   │
   ▼
固件在复位向量启动（SeaBIOS / OVMF）
   │ 读 fw_cfg → 把 ACPI 表搬进 RAM 并发布 RSDP
   │ 枚举 PCI/PCIe（见第 5 节）
   │ 补全/改写部分 ACPI（如 _OSC、PCI 资源）
   ▼
OS 读 ACPI/DT + PCI 配置空间
   ▼
"我看到一块 Q35 + ICH9 的主板"
```

**核心结论**：客户机从不被直接告知机型；它是在固件与 QEMU 共同铺设的
"硬件原语 + 表"之上，**自己推断**出来的。

## 5. 深挖：UEFI 要枚举 PCIe，QEMU 得准备好什么

先记住一句话分工：

> **QEMU 提供"能被枚举的硬件"和"告诉固件去哪枚举的表"；
> 真正的枚举（读 ID、分配 BAR、配中断）由固件（OVMF）在运行时完成。**

QEMU 不预先生成"设备清单"交给固件，而是布置好下面这些"原料"：

### 5.1 配置空间访问通路

- q35：把 ECAM 窗口映射成一段 `MemoryRegion`（`pcie_host_mmcfg_init`），
  并在 ACPI 里生成 `MCFG` 告诉固件 ECAM 基址
- i440fx：提供 `0xCF8/0xCFC` 传统端口

固件据此**逐 bus/dev/func 读配置空间**。

### 5.2 总线 / 桥 / 根端口设备

host bridge、`pcie-root-port`、PCIe-PCI bridge、下游设备，都是真实存在的
`PCIDevice` 对象。固件从 host bridge 开始向下遍历。

### 5.3 每个设备的配置空间内容（**这是要构造的内存内容**）

`PCIDevice.config` 是一个内存缓冲区，QEMU 在设备 `realize` 时把它填好：

- 头 64 字节：Vendor ID、Device ID、Revision、Class Code、Header Type、Cache Line…
- **BAR 寄存器**：写入类型位（内存/IO、32/64 位、prefetchable）
- **能力链表**：PM、**MSI/MSI-X**（含 MSI-X Table/PBA 的 BAR 与偏移）、
  PCIe Capability（Link/Slot 状态）
- **扩展 ROM 指针**（`PCI_ROM_ADDRESS`）

固件枚举时靠三招读取：

```
① 读 Vendor ID（0xFFFF = 该位置无设备）
② 写 BAR = 0xFFFFFFFF，再读回 → 得到大小掩码（QEMU 实现这个"探测"语义）
③ 遍历能力链表，识别 MSI-X 等
```

> 所以答案是：**是的，QEMU 要构造配置空间这块内存内容**。
> 但它不构造"分配结果"——BAR 的最终地址由固件写。

### 5.4 地址窗口（BAR 分配的资源池）

host bridge 向固件声明可用的地址窗口，固件从里面给 BAR 分配：

- 32 位 PCI MMIO 空洞（如 `0x80000000` 起）
- I/O 端口空间
- 64 位 prefetchable 窗口（`pci-hole64`，在 4G 以上）

这些范围写进 ACPI `_CRS`，固件读 `_CRS` 后据此分配。分配完成后，
固件把地址写回每个 BAR，QEMU 的 `pci_update_mappings` 随即把对应
`MemoryRegion` 挂到该地址上——**设备这时才真正"出现在"那段地址**。

### 5.5 ACPI 表 + fw_cfg 投递（**也是构造内存内容**）

- QEMU 生成 `MCFG` / `DSDT` / `FADT` / `MADT` …
- 通过 fw_cfg 的 `etc/acpi/tables` + `etc/table-loader` 交给固件
- 固件把表搬进客户机 RAM、重定位指针、发布 `RSDP`

### 5.6 固件镜像与扩展 ROM

- 固件本身（OVMF）由 QEMU 放在复位向量/pflash（第 21 章），是"构造好的 ROM 内容"
- 设备的**扩展 ROM**（VGA BIOS、PXE）也由 QEMU 放到 ROM 区域，
  通过 `PCI_ROM_ADDRESS` 暴露，固件/OS 可执行

### 5.7 OVMF 实际枚举流程

```
复位 → SEC/PEI/DXE 初始化
  → 读 MCFG 得到 ECAM 基址
  → for bus 0..255: for dev: for func:
       读 Vendor ID；发现设备
       探测 BAR 大小、遍历能力
  → 从地址窗口分配 BAR / 桥窗口，写回
  → 配置 MSI-X / INTx 路由
  → 生成面向 OS 的 ACPI（PCI 根资源、_OSC）
  → BDS 按 BootOrder 找引导目标 → 交棒
```

### 5.8 小结表：QEMU vs 固件 的职责

| 事项 | QEMU 做 | 固件(OVMF)做 |
| --- | --- | --- |
| 配置空间访问通路 | ✅ 映射 ECAM / CF8 | 使用 |
| 设备配置空间内容 | ✅ 构造 ID/BAR/能力 | 读取 |
| BAR 大小探测语义 | ✅ 实现"写全 1 读回" | 发起探测 |
| BAR 地址分配 | ❌ | ✅ |
| 地址窗口声明 | ✅ ACPI `_CRS` | 读取并分配 |
| ACPI 表构造 | ✅ 生成字节流 | 搬运/补全/发布 |
| 中断路由 | ✅ `_PRT` / MSI-X 支持 | 编程 |
| 枚举结果 | ❌ | ✅ |

**所以"要不要构造内存内容"的准确回答**：
QEMU 要构造的是**原料**——固件镜像、每个设备的 PCI 配置空间、option ROM、
ACPI/SMBIOS 表（经 fw_cfg）、地址映射；**枚举的结果（BAR 地址、桥窗口）不构造**，
由固件运行时决定。

## 6. ARM 视角：`virt` 为什么没有 q35 那种二选一

（这一节是第 22 章的 ARM 对照。）

### 6.1 ARM 也要选机型

```bash
qemu-system-aarch64 -machine virt,accel=tcg,gic-version=3 ...
```

这里的 `-machine virt` **就是机型选择**，`virt` 大致相当于 ARM 世界的 q35。
它同样版本化：`virt-8.2`、`virt-7.0`…，`virt` 只是"最新版"别名。

### 6.2 为什么没有 i440fx/q35 那种二选一

因为 **q35 / i440fx 是真实芯片组**：

- `pc-i440fx` = Intel 440FX + PIIX3（1996）
- `pc-q35` = Intel Q35 MCH + ICH9（2009）

x86 有几十年 PC 向下兼容包袱，所以要保留多套芯片组。而 ARM 的 `virt` 是
**QEMU 定义的标准虚拟平台**，不是模拟某块真板子，于是"一套通吃"：

```
virt 提供：GICv2/v3(+ITS)、generic timer、PL011 UART、
          up to 32 个 virtio-mmio、GPEX PCIe host bridge、
          pl031 RTC、GPIO、EFI 等
```

### 6.3 ARM 上"拧芯片组"的地方是 machine 参数

| 参数 | 作用 | 类比 x86 |
| --- | --- | --- |
| `gic-version=2\|3\|max` | 中断控制器版本 | 中断模型选择 |
| `its=on\|off` | GICv3 的 MSI 控制器（PCIe MSI 要用） | MSI/MSI-X 支持 |
| `pci=on\|off` | 是否有 PCIe 根桥 | 有无 PCIe |
| `iommu=on` | SMMU | vIOMMU |
| `highmem=on` | RAM 放到 4G 以上 | above-4g |
| `virtualization=on` | EL2（嵌套虚拟化） | VMX/SVM 透传 |
| `secure=on` | EL3 / TrustZone | firmware level |

### 6.4 ARM 也有"真板子"机型

| 机型 | 模拟对象 |
| --- | --- |
| `virt` | QEMU 通用虚拟平台（默认首选） |
| `raspi3b` / `raspi4b` | 树莓派 |
| `vexpress-a9` / `vexpress-a15` | Versatile Express |
| `sbsa-ref` | ARM 服务器参考平台 |
| `xlnx-zcu102` | Xilinx ZynqMP |

### 6.5 ARM 的 PCIe 枚举同样依赖 ITS/GICv2m

和 x86 一样，`virt` 的 PCIe 要能被固件枚举，也需要中断配套：

- GICv3：加 `its=on` 后 PCIe 设备才方便用 **MSI**
- GICv2：用 GICv2m 提供 MSI
- 否则设备退化为 INTx

### 6.6 一段 ARM 命令的逐项点评

```bash
qemu-system-aarch64 \
    -machine virt,accel=tcg,gic-version=3 \   # ← 机型 + 中断版本
    -cpu cortex-a72 \                          # ← CPU 型号（≈x86 -cpu）
    -m 2G -smp 2 \
    -drive file=alpine-virt-...-aarch64.iso,media=cdrom,readonly \
    -drive file=alpine-arm.qcow2,format=qcow2,if=virtio \
    -netdev user,id=n0 \
    -device virtio-net-pci,netdev=n0 \         # ← 走 PCIe，建议配 its=on
    -device virtio-gpu-pci \
    -bios /usr/share/qemu-efi/QEMU_EFI.fd \    # ← 只读，变量不持久化
    -vnc :0
```

四个常踩的点：

1. **`-bios` 路径**：ARM UEFI 常装到 `/usr/share/qemu-efi-aarch64/QEMU_EFI.fd`
   或 `/usr/share/AAVMF/`，先确认文件存在
2. **缺 vars**：`-bios` 是只读 ROM，UEFI 变量重启即丢；要持久化用两块 pflash
   （和 x86 完全同理，见第 21 章）
3. **`gic-version=3` + PCIe**：想用 MSI 就加 `its=on`
4. **TCG 慢**：跨架构（x86 宿主跑 aarch64）只能 TCG，装系统很慢，
   建议用 cloud image + virtio 减少交互

## 7. 小结

- 客户机**看不见"机型"**，它看到的是总线拓扑 + 配置空间 + 地址映射 +
  ACPI/DT + SMBIOS 的并集
- 机型差异通过 6 条通道生效：**总线 / 配置空间 / MemoryRegion / ACPI / SMBIOS / fw_cfg**
  （ARM 再加 Device Tree）
- UEFI 枚举 PCIe 时：**QEMU 造原料，固件做枚举**
- QEMU 要构造的内存内容：**固件镜像、PCI 配置空间、option ROM、ACPI/SMBIOS 表**
- QEMU **不**构造枚举结果（BAR 地址由固件分配）
- ARM 也要选机型，`virt` 之于 ARM ≈ `q35` 之于 x86；只是 `virt` 不是真芯片组
- ARM 的"芯片组开关"在 machine 参数里：`gic-version` / `its` / `pci` / `iommu`…

## 8. 思考题

1. 如果 QEMU 不生成 `MCFG`，q35 上固件还能找到 ECAM 吗？还有什么办法能发现它？
2. 为什么 BAR 的"大小探测"（写全 1 再读回）必须由设备端实现，而不是固件凭空猜？
3. 客户机 OS 在启动后重新枚举 PCI，和固件枚举的结果会冲突吗？谁说了算？
4. ARM `virt` 用 Device Tree 而非 ACPI 时，`lspci` 的信息从哪来？
5. 把一台 VM 从 `pc-i440fx` 迁到 `q35`，为什么客户机很可能直接蓝屏/panic？

1. 不能。q35 的 ECAM 窗口位置要靠 ACPI `MCFG` 表才能被固件/OS 正式获知，没有它固件就不知道该把扩展配置空间映射到哪里。理论上可以硬编码平台约定或从命令行/其它信息推断，但那不可移植也不合规范；固件也可以退回到 q35 同样提供的 `CF8/CFC` 传统访问，但那样读不到 PCIe 的扩展配置空间（超过 256 字节）。所以正规途径必须由 QEMU 生成 `MCFG`。
2. BAR 大小取决于设备自身需要多少 MMIO 地址，固件无法预知，所以必须由设备端实现"写全 1、读回得到大小掩码"的探测语义。QEMU 在设备 realize 时按其 `MemoryRegion` 大小实现这个行为，固件据此分配资源。若没有这个语义，固件只能凭空猜测，极易分配错误导致设备不可用。
3. 通常不会真正冲突：固件枚举并编好 BAR 后，OS 一般尊重并复用这些分配，只做读取和少量必要调整；若 OS 因资源不足决定重分配，会按标准流程改写 BAR，QEMU 的 `pci_update_mappings` 随即更新映射。总之是后写者生效、最终由 OS 说了算，但双方遵循同一套 BAR/窗口语义，所以不会打架。
4. 来自内核自己的 PCI 枚举：Device Tree 只告诉内核 host bridge/ECAM 等平台信息，内核据此用 ECAM 或 `CF8/CFC` 逐个读设备配置空间，得到 vendor/device ID 后生成用户态可见的 PCI 列表。也就是说 DT 提供"从哪枚举"，配置空间提供"枚举到了什么"，`lspci` 读的是后者。
5. 因为换机型等于换了一整块主板：host bridge 的 vendor/device ID、总线拓扑（`pcie.0` vs `pci.0`）、SATA 由 IDE 变 AHCI、ACPI 表（DSDT/MCFG 等）与地址布局全变，guest 里针对旧芯片组加载的驱动、枚举结果和 ACPI 期望全部失配。尤其引导路径和 ACPI 解释不同，内核往往找不到根设备或直接 panic/蓝屏。正确做法是迁移时保持机型不变，跨芯片组只能重装或不做迁移。

</details>
