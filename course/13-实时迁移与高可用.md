# 13 · 实时迁移与高可用

> 把 VM 在物理机之间搬走，**业务不感知**——这是云最性感的特性之一。

## 学习目标

- 理解迁移的完整流程（迭代复制 + 切换）
- 能区分 pre-copy / post-copy / hybrid
- 知道 HA 方案的设计
- 能诊断迁移失败

## 1. 为什么需要迁移

| 场景 | 价值 |
| --- | --- |
| 主机维护 | 把 VM 临时搬走，下线维护 |
| 负载均衡 | 调度到空闲主机 |
| 节能 | 集中到少数主机，关掉空闲 |
| 灾难恢复 | 跨机房迁移 |
| 滚动升级 | 硬件更换 |

## 2. 迁移类型

### 2.1 离线迁移（offline）

VM 关机 → 复制磁盘 + 内存 → 新主机启动。停机时间 = VM 启动时间。

### 2.2 在线迁移（live）

VM 不停机迁移。停机时间 = VM「冻结 + 恢复」的几百毫秒。

### 2.3 sub-second 停机

现代 KVM 在内存 dirty rate 不高的情况下，停机 < 100ms。

## 3. pre-copy 迁移流程（默认）

```
源端                          目标端
 │                              │
 │── 1. 推送 VM 全部内存 ───────►│
 │                              │
 │── 2. 标记 VM 只读，复制脏页 ──►│ (迭代)
 │                              │
 │... dirty rate < 阈值 ...     │
 │                              │
 │── 3. 停 VM                   │
 │── 4. 推送最后一轮脏数据 + 状态 │
 │── 5. 目标端启动 VM ──────────►│
 │                              │
 │── 6. 通知网络（ARP/路由） ────►│
 │                              │
 ▼                              ▼
 旧主机继续                   新主机接管
```

**关键迭代**：

- 每轮复制剩余脏页
- 剩余脏页 < 阈值（默认 50 MB）就停 VM
- 停机时间 = 最后一次推送 + 目标端启动

## 4. post-copy 迁移

```
源端                          目标端
 │                              │
 │── 1. 停 VM                   │
 │── 2. 推送 CPU 状态 + 控制 ──►│
 │── 3. 目标端启动 VM ──────────►│
 │                              │
 │── 4. 客户机继续跑，缺页时 ───►│
 │     目标端向源端请求          │
 │                              │
 │... 内存逐步搬过来 ...        │
 │                              │
 ▼                              ▼
```

**优点**：停机时间 < 100ms（比 pre-copy 还短）
**缺点**：网络故障 = VM 挂；性能抖动

## 5. hybrid / auto-converge

QEMU/KVM 默认策略：pre-copy + 监控 dirty rate，自动 throttle guest（让客户机慢一点，减少脏页），避免震荡。

```bash
virsh migrate --live --auto-converge vm \
    --desturi qemu+ssh://host2/system
```

## 6. 实战步骤（lab09 详写）

### 6.1 前置

```bash
# 共享存储
# 两机互信
# libvirt 版本一致
# CPU model 兼容
```

### 6.2 源端配置

```xml
<domain>
  ...
  <devices>
    <disk ...>
      <source file='/mnt/nfs/vm.qcow2'/>   <!-- 共享 -->
      <shareable/>                          <!-- 必须 -->
    </disk>
  </devices>
  ...
</domain>
```

### 6.3 触发

```bash
virsh migrate --live vm \
    --desturi qemu+ssh://host2/system \
    --persistent \
    --undefinesource \
    --bandwidth 100 \
    --timeout 3600
```

### 6.4 验证

```bash
# host2
virsh list
# 应该看到 vm
```

## 7. 迁移调优参数

```bash
virsh migrate --live vm \
    --desturi qemu+ssh://host2/system \
    --bandwidth 200 \               # MB/s
    --auto-converge \                # 自动 throttle
    --postcopy \                     # 用 post-copy
    --parallel \                     # 多个连接并发
    --timeout 3600
```

XML 写：

```xml
<migration_features>
  <live/>
  <postcopy/>
  <transports>
    <uri type='ssh'/>
  </transports>
</migration_features>
```

## 8. 失败模式

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `unknown OS` | libvirt 版本差 | 升级 |
| 共享盘报错 | disk 没 `shareable` | 加 |
| 跑到 99% 卡住 | dirty rate > 带宽 | auto-converge + 升带宽 |
| 目标端 VM 起不来 | CPU model 不一致 | 统一用 `kvm64` |
| 迁移后网络断 | ARP 没更新 | 检查路由器 |
| 迁移后 IP 变 | DHCP 不同网段 | 静态 IP 或 DHCP relay |

## 9. 高可用方案

### 9.1 KubeVirt + K8s

VM 当 Pod 管理，由 k8s scheduler + node controller 自动迁移。

### 9.2 oVirt / RHV

```xml
<!-- 自动迁移策略 -->
<cluster>
  <migration>
    <auto_converge>true</auto_converge>
    <bandwidth>100</bandwidth>
  </migration>
</cluster>
```

### 9.3 pacemaker + libvirt

```bash
pcs resource create vm-vip ocf:heartbeat:VirtualIP ...
pcs resource create vm-migrate ocf:libvirt:migrate ...
```

### 9.4 自定义 watchdog

```bash
# 心跳 + 故障时迁移
while true; do
    if ! ping -c 1 vm-host; then
        virsh migrate --live vm --desturi qemu+ssh://standby/system
    fi
    sleep 5
done
```

## 10. 存储迁移 vs 完整迁移

| 维度 | 仅内存迁移 | 完整迁移（disk + memory） |
| --- | --- | --- |
| 共享存储要求 | ✅ | ❌ |
| 时间 | 短 | 长（受 disk size 影响） |
| 带宽 | 高 | 中 |
| 风险 | 低 | 中 |

完整迁移示例：

```bash
virsh migrate --live vm \
    --desturi qemu+ssh://host2/system \
    --copy-storage-all
```

## 12. 小结

- pre-copy 是默认，平衡停机时间和成功率
- post-copy 极短停机但脆弱
- 共享存储 + CPU 一致是迁移前提
- HA 用 KubeVirt / oVirt / pacemaker 组合
