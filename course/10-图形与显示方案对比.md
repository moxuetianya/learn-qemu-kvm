# 10 · 图形与显示方案对比

> VM 「画面」怎么呈现给用户，是 VNC？SPICE？还是 GPU 直通？

## 学习目标

- 能区分 VNC / SPICE / virtio-gpu 的能力
- 知道 SPICE 为何适合桌面虚拟化
- 理解 GPU 直通与 vGPU 的取舍
- 能在生产场景里选对方案

## 1. 全景

```
┌─────────────────────────────────────┐
│  客户机 OS                            │
│  显卡驱动（QXL / VGA / virtio-gpu）   │
└─────────────────┬───────────────────┘
                  │ 帧数据
┌─────────────────▼───────────────────┐
│  QEMU / vhost-user-gpu               │
│  后端：画 frame → 编码 → 协议         │
└─────────────────┬───────────────────┘
                  │ 网络协议（VNC/RDP/SPICE）
┌─────────────────▼───────────────────┐
│  客户端（VNC viewer / remote-viewer）  │
└─────────────────────────────────────┘
```

## 2. 三种主流方案

### 2.1 VNC

- 协议：RFB（Remote Frame Buffer）
- 编码：raw / ZRLE / Tight
- 特点：**最简单、几乎通用**

```bash
-vnc :0                    # 5900
-vnc 127.0.0.1:0,password  # 加密码
```

**优势**：
- 几乎所有设备都有 VNC 客户端
- 实现简单，调试友好

**劣势**：
- 不支持视频流加速（每帧重传）
- 单连接，不能多端同时看

### 2.2 SPICE

- 协议：开源的 SPICE 协议
- 编码：图像变化推送、quic、mjpeg
- 特点：**为桌面虚拟化设计**

```bash
-spice port=5900,addr=127.0.0.1,password=xxx,disable-ticketing=on
```

**优势**：
- 视频流（spice-vdagent 后，4K 视频流畅）
- 多端连接（多人同时看）
- USB 重定向
- 双向剪贴板、文件拖拽

**劣势**：
- 客户端主要是 remote-viewer（virt-viewer）
- 实现复杂度高

### 2.3 RDP（微软）

不是 QEMU 原生支持，得借助 XRDP / VNC-RDP 网关。

### 2.4 QXL 与 virtio-gpu：先分清「虚拟显卡」这一层

§2.1–2.3 讲的是**显示协议**（像素怎么送到客户端），但还有一块拼图：**guest 里的显卡本身是什么设备**。QEMU 主流的有两个：

| | QXL | virtio-gpu |
| --- | --- | --- |
| 定位 | 为 SPICE 远程桌面定制的老设备 | 标准 virtio 半虚拟化设备（新部署推荐默认） |
| guest 驱动 | `xserver-xorg-video-qxl`，仅 X11 | 内核 `virtio_gpu` + Mesa，X11/Wayland 通用 |
| 2D 路径 | guest 发绘图命令，QEMU 在**宿主机 CPU** 上逐条模拟执行 | guest 自己画好整帧，DMA 零拷贝交给宿主 |
| 3D 加速 | ❌ 无 | virgl / venus（见 [27 章](27-虚拟机使用GPU.md)） |
| render node | 无（只暴露 `card0`） | virgl 开启后有 `renderD128` |
| 稳定性 | 高分辨率/多屏问题多 | 更稳定 |

**效率结论：绝大多数场景 virtio-gpu 更快、更省 CPU。** 一个常见误解是 QXL 的「2D 加速」用了什么硬件——没有，那些绘图命令是 QEMU 进程在宿主机 CPU 上模拟执行的；而 virtio-gpu 的 2D 模式更朴素：guest 把整帧画好，经 virtio 共享内存直接送出。QXL 的真正优势只剩 SPICE 远程桌面的命令级增量传输（见 §5.4），且已处于维护模式。

### 2.5 virtio-gpu

不算「远程显示协议」，而是「GPU 模拟器」——它与显示协议的分层关系见 §5.4。

| 模式 | 用途 |
| --- | --- |
| 无 virgl | 2D 高效帧传输 |
| virgl | 3D 加速（OpenGL 4.x） |
| venus | Vulkan（实验） |

```xml
<video>
  <model type='virtio' heads='1' virgl='on'/>
</video>
```

**优势**：3D 性能接近原生
**劣势**：需要 Linux 5.x+，Windows 客户端少

> 「无 virgl = 2D 加速」的精确含义：只是高效的帧传输，**并不使用宿主机 GPU**——guest 里所有绘制由 guest CPU 软件完成。开了 virgl 后，guest 的 OpenGL 才真的跑在宿主物理 GPU 上（分层模型见 [27 章 §1](27-虚拟机使用GPU.md)）。

| 3D 性能 | ❌ | ★ | ★★★★ | ★★★★★ |

## 4. 各方案适用场景

| 场景 | 推荐 |
| --- | --- |
| 服务器维护（无 GUI） | VNC |
| 普通办公桌面 | SPICE |
| 远程工作站 / 设计 | GPU 直通 + SPICE |
| AI 训练 / CUDA | GPU 直通 + RDP |
| 游戏云 | GPU 直通或 vGPU |
| 大屏展示 | SPICE |

## 5. SPICE 进阶

### 5.1 启用 vdagent

客户机装 spice-vdagentd：

```sh
apk add spice-vdagent  # Alpine
apt install spice-vdagent  # Debian/Ubuntu
```

效果：

- 客户机分辨率自适应客户端窗口
- 剪贴板共享
- USB 重定向（需要客户端支持）

### 5.2 多端连接

```bash
# QEMU 启动
-spice port=5900,password=xxx
# 多个 client 连同一端口，可同时看
```

### 5.3 TLS 加密

```bash
-spice port=5901,tls-port=5901,\
      x509-dir=/etc/pki/libvirt-spice,\
      tls-channel=main,plaintext-channel=input
```

### 5.4 SPICE 与虚拟 GPU：分层解耦，合作深度不同

「用 SPICE 是不是就得配 QXL？」——不是，它们在不同的层：

```
guest 应用 ──▶ guest 驱动 ──▶ 虚拟显卡设备(QEMU) ──▶ 显示后端
  (画)          (qxl / virtio_gpu)  (产生画面)       (SPICE / VNC / gtk 窗口)
```

显示后端与设备**自由组合**，但合作深度不同：

| 组合 | 效果 |
| --- | --- |
| QXL + SPICE | 设计场景：绘图命令几乎一一对应翻译成 SPICE 协议消息，命令级增量、客户端资源缓存 |
| QXL + VNC | ❌ 最差组合：QEMU 得把命令软件渲染成帧，两头吃亏 |
| virtio-gpu + SPICE | 现代通用组合：帧级差分 + vdagent |
| virtio-vga-gl + SPICE `gl=on` | 宿主 GPU 渲染后串流 |

两个方向的不对称结论：

- **选 SPICE ≠ 必须选 QXL**：virtio-gpu + SPICE 完全可用，Wayland guest 基本只有这个组合合理（QXL 没有 Wayland 驱动）
- **选了 QXL 就该配 SPICE**：离开 SPICE，QXL 的命令级优势全没了
- 剪贴板同步、分辨率自适应来自**协议 + vdagent**（§5.1），与虚拟显卡选哪个无关

## 6. GPU 直通实战

### 6.1 硬条件

- 主板 BIOS 打开 VT-d / IOMMU
- GPU 在独立 IOMMU group
- 足够大页（建议 1GB hugepage）

### 6.2 步骤

```bash
# 主机绑定 vfio-pci
echo "vfio-pci" > /sys/bus/pci/devices/0000:01:00.0/driver_override
echo "0000:01:00.0" > /sys/bus/pci/drivers/vfio-pci/bind

# 启动 VM
qemu-system-x86_64 \
    -machine q35,accel=kvm \
    -cpu host,kvm=on,vendor=GenuineIntel \
    -m 16G -smp 8 \
    -drive file=vm.qcow2,format=qcow2,if=virtio \
    -device vfio-pci,host=01:00.0,x-pci-vendor-id=0x10de,x-pci-device-id=0x1c03 \
    -vga none \
    -display none \
    -spice port=5900,password=xxx
```

### 6.3 性能

| 应用 | 直通前 | 直通后 |
| --- | --- | --- |
| CUDA 训练 | 不可用 | 95% 原生 |
| 4K 视频播放 | 30fps | 60fps |
| OpenGL 4.x | ❌ | ✅✅ |

## 7. SR-IOV 与 vGPU

### 7.1 NVIDIA vGPU

把一张数据中心 GPU（如 A40）分成多个 vGPU（如 1q / 2q / 4q），每个 VM 用一份。

优点：
- 多个 VM 共享 GPU
- 帧缓冲隔离
- 接近原生性能

缺点：
- License 贵
- 受支持的 GPU 型号少

详见 08 章。

## 9. 优劣对比速记

| 需求 | 推荐 |
| --- | --- |
| 远程桌面 | SPICE + vdagent |
| 视频播放 | GPU 直通 |
| AI / CUDA | GPU 直通 |
| 移动办公 | SPICE |
| 服务端（无 GUI） | VNC |

## 10. 小结

- **VNC** = 简单通用
- **SPICE** = 桌面虚拟化首选（需要 vdagent）
- **virtio-gpu** = 虚拟化里的 3D 加速；2D 模式不用宿主 GPU，开 virgl 才用
- **QXL** = SPICE 时代的专用显卡，新部署默认 virtio-gpu；选了 QXL 就配 SPICE，virtio-gpu 与任意后端组合（§5.4）
- **GPU 直通** = 极致性能，需要硬件 + 操作系统支持

## 11. 思考题

1. SPICE 比 VNC 多哪些能力？代价是什么？
2. GPU 直通后，VM 的「显示器」在哪？
3. vGPU 和 SR-IOV 是一回事吗？
4. virtio-gpu 用 virgl 与 GPU 直通，性能差几个数量级？
5. 为什么「QXL + VNC」是最差的组合？virtio-gpu 2D 模式既然也不用宿主 GPU，为什么通常还比 QXL 快？

<details>
<summary>参考答案（先自己想再看）</summary>

1. SPICE 多了视频流编码（mjpeg/quic，配 spice-vdagent 后 4K 视频流畅）、多客户端同时连接、USB 重定向、双向剪贴板与文件拖拽、客户机分辨率自适应。代价是实现复杂、带宽和 CPU 开销更高，客户端基本只有 remote-viewer（virt-viewer），生态远不如几乎万物皆有的 VNC 客户端。
2. 物理 GPU 直通给 VM 后，显示输出在客户机一侧，但通常没有真实显示器插在直通卡上，画面要么由客户机自己采集，要么（更常见）通过 SPICE/RDP 等远程协议把虚拟桌面编码传出，或依赖云游戏/虚拟显示方案。所以「显示器」是客户机里的逻辑虚拟显示设备，物理呈现靠远程协议完成。
3. 不完全是一回事。vGPU 主要是 GPU 厂商（如 NVIDIA vGPU/GRID）把一张物理 GPU 切成多个带帧缓冲隔离的虚拟 GPU，是专有方案且需要授权；SR-IOV 是 PCIe 标准的硬件功能，把 PF 暴露成多个 VF 直通给 VM，也用于网卡。两者都能实现多 VM 共享一块设备，但机制和来源不同。
4. 通常差一个数量级以上。virgl 是命令转发与宿主 GPU 共享渲染，路径长、要等宿主渲染再回传，3D 性能往往只有直通的几成甚至更低；GPU 直通让 VM 直接驱动物理 GPU，CUDA/OpenGL 可接近原生的九成以上。所以极致 3D/AI 用直通或 vGPU，virtio-gpu+virgl 只适合轻量 3D。
5. QXL 的设计前提是 guest 的绘图命令能被翻译成 SPICE 协议消息做命令级增量；接 VNC 后这层优势作废，QEMU 还必须把命令在宿主 CPU 上软件渲染成完整帧，再套 VNC 的帧级协议——两层开销叠加。virtio-gpu 2D 虽然也只是帧传输，但 guest 渲染完的帧经 virtio 共享内存 DMA 直出，没有「命令模拟渲染」这一跳，路径更短、宿主 CPU 占用更低（§2.4/§5.4）。

</details>
