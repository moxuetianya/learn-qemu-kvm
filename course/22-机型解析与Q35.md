# 22 · 机型解析与 Q35 芯片组

> `-machine q35` 这短短几个字符背后，是一整套「版本化的虚拟主板」。这章讲清
> 机型怎么被解析、Q35 到底比 i440fx 多造了哪些硬件、这些默认值从哪来。

## 学习目标

- 说清什么是 machine type，为什么它要**版本化**
- 找到 `-machine` 从字符串到 `MachineClass` 的解析路径
- 能画出 Q35 与 i440fx 的硬件拓扑差异
- 会读 `pc_q35_init()`，知道 RAM / MCH / LPC / AHCI 分别在哪一步
- 理解 `compat_props` / `-global` 如何让新代码跑出老行为

## 1. machine type 是什么

一个 machine type（机型）= **一套虚拟主板的完整描述**：有哪些总线、哪些芯片组、
默认挂哪些设备、各个设备的默认参数。QEMU 用它来回答：
「这次要模拟的是哪块板子？」

```
-machine q35,accel=kvm,smm=on
          └┬┘  └──┬──┘ └──┬──┘
         机型   属性1     属性2   （属性会覆盖机型的默认值）
```

### 1.1 为什么要版本化

QEMU 会不断改进设备模型（改默认值、修 bug、加特性）。如果"q35"永远指向最新行为，
那么一次 QEMU 升级就可能让**同一份配置的 VM 行为改变**——迁移、热插拔、
甚至能不能开机都可能受影响。

解决办法：**机型带版本号**，并冻结老版本的行为。

```bash
qemu-system-x86_64 -machine help
# pc-i440fx-8.2   Standard PC (i440FX + PIIX, 1996)
# pc-q35-8.2      Standard PC (Q35 + ICH9, 2009)
# q35             → 最新 pc-q35-* 的别名
# pc              → 最新 pc-i440fx-* 的别名
```

> 生产里的 VM 一般固定写死 `pc-q35-8.2`，不写 `q35`。
> 升级 QEMU 后行为不变，要迁移到新版本机型时才手动切。

## 2. 源码位置

```
hw/
├── core/
│   └── machine.c        # MachineClass / MachineState 基类，-machine 解析
└── i386/
    ├── pc.c             # PC 家族公共逻辑（内存、基本设备）
    ├── pc_q35.c         # Q35 机型：TYPE_Q35_MACHINE + pc_q35_init
    ├── pc_piix.c        # i440fx 机型：TYPE_PIIX4_PC
    └── pc_sysfw.c       # 固件（第 21 章）
```

关键结构：

```c
/* include/hw/boards.h（简化） */
struct MachineClass {
    const char *name;          /* "pc-q35-8.2" */
    const char *alias;         /* "q35" */
    const char *desc;          /* 人类可读描述 */
    void (*init)(MachineState *state);   /* ← 建板子的函数，pc_q35_init */
    const char *default_cpu_type;
    const char *default_machine_opts;
    GlobalProperty *compat_props;        /* ← 版本兼容参数 */
    bool no_floppy, no_cdrom, no_parallel, ...;
};

struct MachineState {
    Object parent_obj;
    ram_addr_t ram_size;
    const char *cpu_type;
    ...
};
```

## 3. 解析路径：从 `-machine q35` 到 `MachineClass`

```c
/* softmmu/vl.c（简化） */
static void machine_opts_parse(void)
{
    /* 遍历所有 -machine / -M，逐个交给 machine_parse() */
    qemu_opts_foreach(qemu_find_opts("machine"),
                      machine_parse, NULL, &error_fatal);
}

/* hw/core/machine.c（简化） */
MachineClass *machine_parse(const char *name, GSList *machines, Error **errp)
{
    ...
    mc = find_machine(name, machines);   /* 先精确匹配 name，再匹配 alias */
    if (!mc) {
        /* 支持 "q35,prop=val,prop2" 形式，先按逗号切开取机型名 */
    }
    if (is_help_option(s)) { list_machines(); exit(0); }
    return mc;
}
```

之后在 `qemu_init()` 里：

```c
    machine_class = select_machine();      /* 拿到 MachineClass */
    current_machine = MACHINE(object_new_with_typename(
        object_class_get_name(OBJECT_CLASS(machine_class))));
    /* 剩下 -machine 里除 type= 外的属性，逐个 set 到 MachineState */
```

**要点**：`-machine` 的属性最终都落到 `MachineState` 的 QOM 属性上，
所以 `-M q35,smm=on` 等价于先 `object_new(Q35)` 再"设 `smm=on`"。

## 4. Q35 vs i440fx：硬件拓扑差在哪

| 组件 | i440fx (1996) | q35 (2009) |
| --- | --- | --- |
| 北桥/内存控制 | 440FX (i440fx-pmc) | Q35 MCH (`q35-pcihost`) |
| 南桥 | PIIX3 | ICH9 (`ich9-lpc`) |
| PCIe | ❌（模拟 PCI） | ✅ 原生 PCIe 根复合体 |
| SATA | IDE (PIIX) | AHCI (`ich9-ahci`) |
| USB | UHCI | UHCI + EHCI |
| 中断/IOMMU | 传统 | 支持 SMM、可选 intel-iommu |

```
i440fx 拓扑                        q35 拓扑
─────────────                     ─────────
 CPU                                CPU
  │                                  │
440FX 北桥 ── RAM                   Q35 MCH ── RAM
  │  PCI 总线(0)                     │  PCIe 根总线 pcie.0
  ├── VGA                            ├── pcie.0 上的 PCIe 设备
  ├── virtio-*                       ├── q35-pcihost 的 PCI 域(0)
  └── PIIX3 南桥                     └── ICH9 南桥 (ich9-lpc)
       ├── IDE / USB / ISA                ├── AHCI / USB / ISA
       └── 中断/PIT/RTC                   └── 中断/PIT/RTC/IOAPIC
```

生产选 q35 的核心理由：**原生 PCIe**。直通 NVMe、vIOMMU、PCIe 热插拔、
更接近真机的拓扑，都能少踩坑。

## 5. `pc_q35_init()` 逐步拆解

机型 `init` 回调就是建板子的主函数：

```c
/* hw/i386/pc_q35.c（大幅简化） */
static void pc_q35_init(MachineState *machine)
{
    PCMachineState *pcms = PC_MACHINE(machine);

    /* 1. CPU：按 -smp 创建，缺省用机型 default_cpu_type */
    pc_cpus_init(pcms);

    /* 2. RAM 与内存拓扑（below-4g / above-4g 布局） */
    pc_memory_init(pcms, machine, &ram_memory);

    /* 3. 北桥：Q35 MCH（host bridge） */
    q35_host_init(pcms, &q35_host);          /* TYPE_Q35_HOST_DEVICE */

    /* 4. LPC/ISA 桥（ICH9） */
    pci_create_simple(host_bus, ...,
                      TYPE_ICH9_LPC_DEVICE); /* ich9-lpc */

    /* 5. 基本设备：RTC / HPET / PIT / i8042 / 串并口 / FDC */
    pc_basic_device_init(pcms, isa_bus,
                         &rtc_state, &hpet, &floppy_controller, ...);

    /* 6. 存储：ICH9 的 AHCI 控制器 */
    pci_create_simple(host_bus, ..., TYPE_ICH9_AHCI);

    /* 7. 显示、网卡 */
    pc_vga_init(...);      /* 若 -vga 未禁用 */
    pc_nic_init(...);      /* 默认网卡（若未 -nic none） */

    /* 8. CPU 热插拔、SMBIOS、option ROM 等收尾 */
    x86_cpu_plug_init(pcms);
}
```

对照第 20 章的流程图：`machine_run_board_init()` → `mc->init()`（就是它）
→ 一堆 `qdev_realize()` → 固件就位。

## 6. 默认参数从哪来

机型不是"一个函数"，而是一层层覆盖：

```
MachineClass 基础默认
   │
   ├─ pc_q35_machine_options()      定 Q35 家族默认（无 floppy、无并口…）
   │
   ├─ pc_q35_8_2_machine_options()  8.2 版本特有默认
   │
   └─ -machine q35,<属性>=<值>      用户在命令行最后覆盖
```

```c
/* hw/i386/pc_q35.c（简化） */
static void pc_q35_machine_options(MachineClass *m)
{
    m->family = "pc_q35";           /* 家族名，用于按家族匹配 */
    m->desc = "Standard PC (Q35 + ICH9, 2009)";
    m->default_cpu_type = X86_CPU_TYPE_NAME("qemu64");
    m->no_parallel = 1;
    m->no_floppy = 1;
    m->no_cdrom = 1;
    m->pci_info.w32.begin = 0x80000000;   /* 32 位 PCI 窗口 */
    ...
}
```

所以你在 `-machine help` 里看到的一条条默认行为，本质都是这些字段。

## 7. 兼容机制：`compat_props` 与 `-global`

版本化机型要"新代码跑出老行为"，靠的是 **global properties（全局属性）**：

```c
/* hw/core/machine.c（简化）：把机型带的 compat_props 全部注册 */
void machine_register_compat_props(MachineState *machine)
{
    MachineClass *mc = MACHINE_GET_CLASS(machine);
    if (mc->compat_props) {
        qdev_prop_register_global_list(mc->compat_props);
    }
}
```

比如新版本把某个设备的默认值改了，老机型就会挂一条
`{ driver = "virtio-blk", property = "x-something", value = false }`，
把它压回旧值。

你也可以手动干预：

```bash
-machine q35 -global virtio-blk-pci,property=seg_max,value=126
# 或针对具体设备实例
-device virtio-blk-pci,id=blk0,drive=disk0
```

> 这套机制是 QEMU 迁移兼容性的基石：**机型版本 + global props 决定了 VM 的"形状"**。

## 8. 实战：把机型"看穿"

```bash
# 1. 列出所有机型
qemu-system-x86_64 -machine help

# 2. 看某个机型能配哪些属性
qemu-system-x86_64 -M q35,help
#   accel=...
#   kernel_irqchip=...
#   smm=on|off
#   pflash0=...
#   ...

# 3. 起一台，冻结，看设备树/内存树
qemu-system-x86_64 -machine q35,accel=kvm -m 512 -display none -S -monitor stdio
(qemu) info qtree
(qemu) info mtree -f
(qemu) info qom-tree | head -50
```

对比实验：分别用 `-machine pc` 和 `-machine q35` 起，`info qtree` 里
总线名字、是否有 `pcie.0`、SATA 是 IDE 还是 AHCI，一眼就能看出区别。

### 8.1 常见机型属性

| 属性 | 作用 | 典型值 |
| --- | --- | --- |
| `accel` | 加速器 | `kvm` / `tcg` / `kvm:tcg` |
| `smm` | 开 SMM（Secure Boot 需要） | `on` |
| `kernel_irqchip` | 中断芯片放内核还是用户态 | `on` / `split` / `off` |
| `pflash0` / `pflash1` | 用 `-blockdev` 指定固件 | 见第 21 章 |
| `vmport` | VMware 兼容端口 | `on` / `off` |
| `usb` | 是否默认建 USB | `on` / `off` |
| `graphics` | 默认显卡 | `on` / `off` |

## 9. 小结

- 机型 = 虚拟主板描述，**必须版本化**（`pc-q35-8.2`），别名 `q35` 指向最新
- 解析路径：`-machine` → `machine_parse()` → `MachineClass` → `MachineState`
- Q35 = Q35 MCH + ICH9，**原生 PCIe / AHCI**；i440fx = 440FX + PIIX3
- `pc_q35_init()` 按「CPU → RAM → 北桥 → 南桥 → 基本设备 → 显示网卡」建板
- 默认值层层覆盖：机型家族 → 版本 → 命令行
- `compat_props` / `-global` 是机型行为冻结与迁移兼容的核心

## 10. 思考题

1. 为什么不给机型加版本号，直接总是用最新行为，会有什么后果？
2. `q35` 和 `pc-q35-8.2` 起出来的 VM，`info qtree` 会完全一样吗？什么时候不一样？
3. `-machine pc` 和 `-machine pc-i440fx-8.2` 是同一个东西吗？
4. 如果要把一台老机型（`pc-i440fx-2.9`）的 VM 升级到新机型，需要注意什么？

<details>
<summary>参考答案（先自己想再看）</summary>

1. 若不版本化，QEMU 每次改设备默认值或修 bug 都会改变同一配置 VM 的行为：迁移时源与目的不一致会失败，热插/开机结果也会漂移。版本号把旧行为用 `compat_props` 冻结，使升级 QEMU 不改变既有 VM。这也是生产里要写死 `pc-q35-8.2` 而不是写 `q35` 的原因。
2. 在同一个 QEMU 版本下通常完全一样：`q35` 是别名，指向最新的 `pc-q35-*`，两者解析到同一个 `MachineClass`。但升级 QEMU 后 `q35` 会指向新的 `pc-q35-N`，默认值与 compat 行为可能变化，而 `pc-q35-8.2` 保持旧行为，此时 `info qtree` 才会出现差异（新增设备或改变的默认属性）。
3. 不是永远恒等。`pc` 是最新 `pc-i440fx-*` 的别名，在某个具体版本下等于当前发布号（如 `pc-i440fx-8.2`），家族相同、当下等价。但跨版本升级后 `pc` 会漂移，而 `pc-i440fx-8.2` 固定，所以二者只在该版本下相同。
4. 要确认新机型在默认值与 compat 行为上的差异：设备默认属性（`seg_max`、USB、SATA/AHCI、中断模型等）、host bridge ID 与 ACPI 表都会变，可能触发重新枚举或驱动失配。稳妥做法是先用 `-global`/compat 逐项对齐并做迁移测试；像 2.9 到 8.2 这种跨大版本差异极大，通常建议新建 VM 重装而非直接改机型。

</details>
