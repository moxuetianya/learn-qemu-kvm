# 18 · 与容器、云原生的取舍

> KVM 跟容器不是替代关系，而是「不同抽象层次」。云原生时代，理解两者的边界更重要。

## 学习目标

- 知道 KVM 跟容器在「隔离边界」上的本质差异
- 能判断一个业务该用容器还是 VM
- 理解 KubeVirt、Firecracker、QEMU microVM 等新形态
- 看清「serverless」、「云函数」背后到底是什么

## 1. 一张图看清差异

```
                  ┌─────────────────────────────┐
                  │       容器（共享内核）         │
                  │  ┌─────────┐ ┌─────────┐    │
                  │  │ App1    │ │ App2    │    │
                  │  │ libc    │ │ libc    │    │
                  │  └────┬────┘ └────┬────┘    │
                  │       │ namespace │ cgroup  │
                  ├───────┴───────────┴──────────┤
                  │   Linux 内核（共享）           │
                  └─────────────────────────────┘

                  ┌─────────────────────────────┐
                  │       VM（独立内核）           │
                  │  ┌─────────┐ ┌─────────┐    │
                  │  │ App1    │ │ App2    │    │
                  │  │ libc    │ │ libc    │    │
                  │  │ kernel  │ │ kernel  │    │
                  │  └────┬────┘ └────┬────┘    │
                  │       │ KVM + virtio │        │
                  ├───────┴───────────┴──────────┤
                  │   Linux 内核（共享硬件）       │
                  └─────────────────────────────┘
```

**最本质区别**：容器共享内核，VM 有独立内核。

## 2. 隔离强度对比

| 维度 | 容器 | VM |
| --- | --- | --- |
| **隔离单元** | Linux 进程 | 整个 OS |
| **syscall 攻击面** | 大（容器内可调任何 syscall） | 小（VM 内 syscall 不影响 host） |
| **内核 bug 影响** | 一颗内核挂 = 所有容器挂 | 一颗内核挂 = 只影响该 VM |
| **CPU 隔离** | 受 CFS 调度影响 | 接近原生（hardware-assisted） |
| **内存隔离** | cgroup 隔离（共享内核页） | EPT 隔离（独立页表） |
| **网络隔离** | namespace + iptables | 独立网络栈 |
| **启动速度** | ms 级 | s 级（VM）/ 100ms 级（microVM） |
| **镜像大小** | MB | GB |
| **密度** | 100+ / 主机 | 10-50 / 主机 |
| **性能** | 99%+ 原生 | 95%+ 原生 |

## 3. 何时用容器

- 微服务、HTTP API
- 短时任务（CI / batch）
- 无状态、可水平扩展
- 想用 K8s 编排
- 多语言 / 多框架

## 4. 何时用 VM

- 需要异构 OS（Windows、BSD、Solaris）
- 需要不同内核版本（老 OS）
- 多租户强隔离（金融、政企）
- 内核模块开发、驱动开发
- 跑传统遗留应用
- GPU / 设备直通场景
- 单 VM 性能要求极致（数据库、大模型）

## 5. 新形态：把两者的优点结合

### 5.1 KubeVirt（VM in K8s）

把 VM 当 K8s Pod 管理。运维统一用 kubectl，但里面跑的是 VM。

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm1
spec:
  running: true
  template:
    spec:
      domain:
        devices:
          disks:
          - name: containerdisk
            disk: {}
            bootOrder: 1
      volumes:
      - name: containerdisk
        containerDisk:
          image: kubevirt/virtio-container-disk
```

适用：传统应用上 k8s、混部 VM + 容器。

### 5.2 Kata Containers（VM-as-Container）

容器语义 + VM 隔离。每个容器跑在 microVM 里，启动 < 1s。

```
containerd → Kata Runtime → firecracker / qemu
```

### 5.3 Firecracker（AWS microVM）

AWS Lambda / Fargate 用的 VMM：

- 启动 < 125ms
- 内存 < 5MB
- 安全优先（极简代码）
- 限制热迁移（为了简单）

### 5.4 QEMU microVM

QEMU 的精简模式：

```bash
qemu-system-x86_64 \
    -machine microvm,rtc=on,acpi=off,pcie=off,pic=off,isa-off=off \
    -no-user-config -nodefaults -nographic -no-reboot \
    -kernel vmlinux \
    -append "console=ttyS0 reboot=t panic=-1" \
    -drive file=rootfs.ext4,if=none,id=root,format=raw \
    -device virtio-blk-device,drive=root \
    -device virtio-net-pci,netdev=net0 \
    -netdev tap,id=net0,ifname=tap0,script=no,downscript=no
```

启动 50-100ms。

### 5.5 gVisor（Google）

用户态内核，介于容器和 VM 之间：

```
应用 ──► gVisor (Go 用户态内核) ──► host kernel syscall
```

**优势**：syscall attack surface 大幅缩小（只暴露 N 个）
**劣势**：性能损失 10-50%

## 6. serverless 背后是什么

| 平台 | 形态 |
| --- | --- |
| AWS Lambda | microVM (Firecracker) |
| Google Cloud Run | gVisor / sandboxed container |
| Azure Functions | Hyper-V microVM |
| 阿里云函数计算 | 容器 + microVM |
| Cloudflare Workers | V8 isolate（不是 VM） |

> **serverless ≠ 无服务器**。serverless 是「按调用计费 + 自动扩缩容」，底层还是 VM/容器。

## 7. 混合架构实战

### 7.1 KubeVirt

```bash
# 装 KubeVirt
kubectl apply -f https://github.com/kubevirt/kubevirt/releases/latest/download/kubevirt-operator.yaml
kubectl apply -f https://github.com/kubevirt/kubevirt/releases/latest/download/kubevirt-cr.yaml

# 跑 VM
virtctl start testvm
virtctl console testvm
```

### 7.2 Kata + containerd

```toml
# /etc/containerd/config.toml
[plugins.cri.containerd.runtimes.kata]
  runtime_type = "io.containerd.kata.v2"
```

```bash
ctr run --runtime=kata docker.io/library/alpine:latest test sh
```

## 9. 决策树

```
要跑新 OS / 不同内核？ ─── 是 ──► VM
                          │
                          否
                          ▼
     业务需要强隔离（多租户/合规）？ ─── 是 ──► VM / Kata
                              │
                              否
                              ▼
                       是微服务？ ─── 否 ──► VM
                              │
                              是
                              ▼
                       单 VM 跑多服务 ──► 容器
                              │
                              否
                              ▼
                      已有 K8s？ ── 是 ──► 容器 / KubeVirt
                              │
                              否
                              ▼
                         容器
```

## 11. 小结

- 容器和 VM 是不同抽象层次，**不是替代关系**
- 容器 = 进程隔离，VM = OS 隔离
- 新形态（KubeVirt、Kata、microVM）在尝试结合两者
- 选型看：业务是否需要 OS 隔离、是否要 K8s、是否多租户
