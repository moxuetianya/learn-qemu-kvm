# 02 · 硬件虚拟化（Intel VT-x / AMD-V）

> 这一章告诉你「KVM 到底借了 CPU 什么能力」。看完再读 KVM 源码就不会懵。

## 学习目标

- 能说出 Intel VT-x 的核心数据结构 VMCS 是什么、存什么
- 知道 VM entry / VM exit 是什么、什么时候发生
- 能区分 EPT 和「影子页表」
- 知道为什么必须开 BIOS 里的 VT-x

## 1. 为什么要硬件辅助

x86 的 17 条敏感指令（如 `lgdt`、`ltr`、`mov cr3`）在 ring 1-3 执行时**不抛异常**。所以纯软件方案只能：

1. **动态二进制翻译** —— VMware 早期做法：扫描客户机指令，把敏感指令替换成陷阱调用。代价：每条指令多一层翻译，性能损耗 10-30%。
2. **半虚拟化** —— 让客户机别用敏感指令，直接调 hypercall。代价：Windows 跑不起来。
3. **CPU 加根模式** —— Intel VT-x / AMD-V：CPU 本身多一种「根模式」，敏感指令在非根模式执行时**硬件抛 VM exit**。代价：必须硬件支持。

显然第 3 种最干净。这就是为什么**没有 VT-x / AMD-V，KVM 跑不起来**。

## 2. Intel VT-x 核心概念

### 2.1 两种模式

| 模式 | 谁跑 | 特点 |
| --- | --- | --- |
| **VMX root operation** | 宿主机（VMM） | 类似 ring 0，可访问物理硬件 |
| **VMX non-root operation** | 客户机 | 受限执行，敏感指令触发 VM exit |

CPU 通过 `VMXON` 进入 VMX 操作，再通过 `VMLAUNCH` / `VMRESUME` 在两种模式间切换。

### 2.2 VMCS（Virtual Machine Control Structure）

**VMCS 是 VT-x 的灵魂**。它是一块 4KB 内存，由 VMM 分配，存三类信息：

| 区域 | 内容 | 谁读写 |
| --- | --- | --- |
| **Guest-state area** | 客户机寄存器、段、MSR 等 | VM exit 时由 CPU 自动保存 |
| **Host-state area** | VMM 寄存器等 | VM exit 时由 CPU 自动加载 |
| **VM-exit control / VM-entry control** | 哪些事件触发 exit、exit 后行为 | VMM 配置 |

简化版的「执行流」：

```
VM entry (CPU 硬件)          VM exit (CPU 硬件)
 ─────────────►              ◄─────────────
   加载 Guest-state              保存 Guest-state 到 VMCS
   切到 non-root 模式            加载 Host-state
   开始跑客户机                   切到 root 模式
                                  跳到 VMM 的 exit handler
```

**关键点**：VMCS 的字段多达几百个，但常用就那么十几个。下面是配置 VMCS 一定会碰到的：

- `Pin-Based VM-Execution Controls`：是否用 MSR/IO 位图
- `Processor-Based VM-Execution Controls`：是否启用 EPT、是否允许客户机跑 ring 0
- `Exception Bitmap`：哪些异常触发 exit
- `VM-Exit Controls`：exit 后是否保存调试信息
- `VM-Entry Controls`：entry 时是否进入 long mode（64 位）

### 2.3 一次完整的「VM exit → VMM 处理 → VM entry」

```c
// 极简版 VMM 主循环（伪代码）
while (1) {
    // VM entry — 硬件自动恢复客户机状态
    vmx_vcpu_run(vcpu);

    // 醒来 = VM exit
    reason = vmx_get_exit_reason(vcpu);
    switch (reason) {
        case EXIT_REASON_IO_INSTRUCTION:
            handle_io(vcpu);
            break;
        case EXIT_REASON_EPT_VIOLATION:
            handle_ept_fault(vcpu);
            break;
        case EXIT_REASON_HLT:
            // 客户机 halt，把物理 CPU 让回去
            break;
        default:
            kvm_inject_emulated_instruction(vcpu);
    }
}
```

> 看到「KVM 源码里一大堆 `handle_exit`」，就是这个循环。每个 exit reason 一个分支。

## 3. AMD-V（SVM）

AMD 走的是另一套命名，但本质思路一致：

| Intel 命名 | AMD 命名 |
| --- | --- |
| VMX | SVM |
| VMCS | VMCB |
| VMXON / VMLAUNCH / VMRESUME | VMRUN |
| VM exit | #VMEXIT |
| EPT | NPT（Nested Page Tables） |

代码上 KVM 用 `kvm_x86_ops` 抽象（这俩字母 x86 包含 Intel 和 AMD）：

```c
struct kvm_x86_ops {
    int (*hardware_enable)(void);
    int (*hardware_disable)(void);
    int (*vcpu_create)(struct kvm_vcpu *vcpu);
    void (*vcpu_free)(struct kvm_vcpu *vcpu);
    int (*vcpu_reset)(struct kvm_vcpu *vcpu, u64 init_event);
    void (*vcpu_load)(struct kvm_vcpu *vcpu, int cpu);
    void (*vcpu_put)(struct kvm_vcpu *vcpu);
    int (*vcpu_run)(struct kvm_vcpu *vcpu);
    int (*handle_exit)(struct kvm_vcpu *vcpu);
    // ... 几十个
};
```

`kvm-intel.ko` 和 `kvm-amd.ko` 分别实现这套结构体。**这就是为什么 KVM 一份代码支持两套硬件**。

## 4. 内存虚拟化：EPT / NPT

### 4.1 为什么需要「两阶段翻译」

普通进程（无虚拟化）：

```
虚拟地址 (VA)  ────页表────►  物理地址 (PA)
```

加了 VM 后：

```
GVA  ────客户机页表────►  GPA  ────EPT/NPT────►  HPA
```

**E**xtended **P**age **T**ables（Intel）/ **N**ested **P**age Tables（AMD）：由 VMM 维护的第二阶段页表。

### 4.2 EPT 怎么避免「影子页表」的坑

老方案（影子页表）：

- VMM 监听 `mov cr3`
- 把客户机页表复制成「影子页表」
- 客户机的 `CR3` 实际指向影子页表
- 每次客户机修改页表，VMM 都要同步

新方案（EPT）：

- 客户机页表照常填，VMM 只填 EPT
- CPU 硬件在 `tlb miss` 时自动两阶段查
- 客户机根本不知道 EPT 存在

EPT 不仅性能好，**实现也简单了 10 倍**。

### 4.3 EPT 缺页怎么办

EPT miss 时 CPU 触发 VM exit，VMM：

1. 找出 GPA 对应的 HPA（可能是分配新页、交换、映射宿主文件……）
2. 把 GPA → HPA 写入 EPT
3. VM entry 让客户机继续跑

这个流程在 KVM 里就是 `handle_ept_violation()`。

## 5. 中断虚拟化

虚拟化里的中断有两类：

1. **外部中断**：物理网卡、键盘、磁盘控制器来的，物理 CPU 先收到
2. **虚拟中断**：客户机内部触发的（如 `int 0x80`）

### 外部中断的处理

```
物理设备 ──► 物理 CPU
              │
              │  VMM 注册中断时抢占（preempt）
              ▼
             VMM
              │  注入虚拟中断到客户机
              ▼
            客户机 OS 中断处理
```

KVM 用 **LAPIC 虚拟化** 让客户机直接操作「虚拟 LAPIC」，避免每次中断都 VM exit。

## 6. I/O 虚拟化

### 6.1 三种方式（再强调一次）

| 方式 | 原理 | VM exit 频率 |
| --- | --- | --- |
| **全模拟**（e1000、IDE） | 客户机驱动按真实硬件行为编程，VMM 截获每条 PIO/MMIO | 高 |
| **virtio** | 客户机驱动 → 共享内存 → 宿主机后端 | 低 |
| **直通**（IOMMU） | 设备直接 DMA 到客户机内存 | 几乎零 |

### 6.2 IOMMU 是直通的必要条件

为什么？因为 DMA 必须**只**访问客户机的物理内存，否则客户机能直接读写宿主机内存——隔离彻底失效。

IOMMU（Intel VT-d / AMD-Vi）：

- 在设备和内存之间做一次「翻译」
- 让 DMA 只能访问预先授权的页
- 拦截非法 DMA 访问

直通还需要：

- BIOS 打开 VT-d / IOMMU
- 内核加 `intel_iommu=on` 或 `amd_iommu=on`
- 设备在独立 IOMMU group（详见 09 章）

## 7. 优劣对比：什么时候用什么硬件能力

| 能力 | 是否必需 | 性能影响 | 生产是否默认开 |
| --- | --- | --- | --- |
| VT-x / AMD-V | ✅ KVM 必须 | – | 是 |
| EPT / NPT | – | 内存虚拟化必备 | 是 |
| VPID / ASID | – | 减少 TLB flush | 是 |
| APICv | – | 减少中断相关 exit | 是 |
| VT-d / AMD-Vi | 直通才需要 | – | 直通才开 |
| Unrestricted Guest | – | 允许客户机跑在实模式直接启动 | 是 |

## 8. 优劣对比速记

| 场景 | 关键硬件能力 | 检查方法 |
| --- | --- | --- |
| KVM 跑得起来 | VT-x / AMD-V | `egrep -c '(vmx\|svm)' /proc/cpuinfo` |
| 内存虚拟化 | EPT / NPT | `egrep -o '(ept\|npt)' /proc/cpuinfo` |
| PCI 直通 | VT-d / IOMMU | `dmesg \| grep -i iommu` |
| SR-IOV | SR-IOV + VT-d | `lspci -vv \| grep SR-IOV` |

## 9. 实战：检查你机器的能力

```bash
# 1. 是否有 VT-x / AMD-V
egrep -c '(vmx|svm)' /proc/cpuinfo
# 输出 > 0 即可

# 2. 是否有 EPT / NPT
egrep -o '(ept|npt)' /proc/cpuinfo | sort -u
# 期望看到 ept 或 npt

# 3. 内核是否打开 IOMMU
dmesg | grep -i -e DMAR -e AMD-Vi
# 期望看到 IOMMU enabled

# 4. KVM 模块是否能加载
lsmod | grep kvm
# 期望看到 kvm 和 kvm_intel（或 kvm_amd）
```

任何一个期望失败，去 BIOS 检查：
- Intel 平台：`Advanced → CPU Configuration → Intel Virtualization Technology = Enabled`
- AMD 平台：`Advanced → CPU Configuration → SVM Mode = Enabled`
- 部分主板：`VT-d` 也是独立选项，必须单独打开

## 10. 小结

- VT-x / AMD-V 提供硬件辅助：CPU 多一种「根模式」，敏感指令触发 VM exit
- VMCS / VMCB 是 VMM 与硬件的「协议」：几百个字段描述客户机/宿主机的状态
- EPT / NPT 把「两阶段翻译」从软件搬到硬件
- 中断、I/O、内存虚拟化都依赖这套硬件能力
- 直通需要 IOMMU 做 DMA 隔离
